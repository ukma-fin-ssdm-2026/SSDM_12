# Робочий процес команди SSDM_12

Документ описує, як у цьому репозиторії з'являються зміни. Правила обов'язкові для всіх
учасників і узгоджені з [командним статутом](TeamCharter.md), розділи 4 і 8.

---

## 1. Життєвий цикл завдання

```
Issue → призначення й мітки → гілка від main → коміти → Pull Request
      → щонайменше 1 схвалення → зелений CI → злиття → issue закривається
```

1. **Будь-яка робота починається з issue.** Немає issue — немає роботи: інакше внесок
   неможливо простежити.
2. Issue отримує **виконавця (assignee)** і **щонайменше дві мітки**: тип роботи
   (`bug` / `enhancement` / `documentation`) і лабораторну (`lab01`…`lab10`).
3. Виконавець створює гілку від актуального `main`.
4. Pull Request містить у описі рядок `Closes #N` — тоді issue закривається автоматично
   при злитті.
5. Якщо завдання заблоковане іншим — ставимо мітку `blocked` і в коментарі вказуємо, чим саме.

## 2. Гілки

Стратегія — **GitHub Flow**: єдина довгоживуча гілка `main`, усе решта короткоживучі.

| Префікс | Для чого | Приклад |
|---|---|---|
| `feature/` | Нова функція або можливість | `feature/booking-conflict-check` |
| `fix/` | Виправлення дефекту | `fix/timezone-offset` |
| `docs/` | Документація й артефакти `docs/` | `docs/team-charter` |
| `ci/` | Зміни конвеєра | `ci/add-bandit-step` |
| `refactor/` | Рефакторинг без зміни поведінки | `refactor/extract-slot-service` |
| `sign/` | Підпис у командному статуті | `sign/asyakozulina` |

Правила:

- Гілка живе коротко: мета — злити протягом 1–3 днів.
- Прямий push у `main` заблоковано ruleset `main-protection`.
- Після злиття гілка видаляється автоматично.

## 3. Коміти

Формат — [Conventional Commits](https://www.conventionalcommits.org/):
`<тип>: <що змінено і навіщо>`.

| Тип | Коли |
|---|---|
| `feat` | Нова функціональність |
| `fix` | Виправлення дефекту |
| `docs` | Документація |
| `test` | Додані або змінені тести |
| `ci` | Конвеєр і автоматизація |
| `refactor` | Зміна структури коду без зміни поведінки |
| `chore` | Обслуговування: залежності, конфігурації, структура |

```
docs: add team charter with AI usage rules
feat: reject overlapping bookings for the same slot
ci: add repository structure check to pipeline
```

Правила:

- Коміти малі: один коміт — одна завершена думка.
- Повідомлення пояснює **навіщо**, а не переказує diff.
- Кожен комітить під власним акаунтом GitHub. Перед першим комітом:
  ```bash
  git config --global user.name "Ім'я Прізвище"
  git config --global user.email "email@прив'язаний.до.github"
  ```

## 4. Pull Requests

**Автор:**

- Заповнює [шаблон опису PR](.github/pull_request_template.md) повністю, включно з розділом
  про використання ШІ.
- Не схвалює і не мерджить власний PR.
- Відповідає на коментарі огляду; невирішені обговорення блокують злиття.

**Рецензент:**

- Дає відповідь протягом 24 годин з моменту запиту.
- «LGTM» без змісту не вважається оглядом. Мінімум — один конкретний коментар або
  обґрунтоване підтвердження, що зміну перевірено.
- Для коду проходить п'ять критеріїв огляду Лаб 5 — стиль, якість, безпека, фреймворк,
  документація й аналіз ([статут](TeamCharter.md) §11.3) — і перевіряє за чек-листом:
  - [ ] Зміна відповідає тому, що описано в issue.
  - [ ] Код або документ зрозумілий без усних пояснень автора.
  - [ ] Оброблено краєві випадки й помилкові сценарії, а не лише «щасливий шлях».
  - [ ] Немає секретів, токенів і реальних персональних даних.
  - [ ] Згенерований ШІ вміст розкрито в описі PR і перевірено автором.
  - [ ] Нові знахідки Ruff, Bandit, detect-secrets чи pip-audit виправлено або придушено з
        причиною поруч (статут §11.5).
  - [ ] Конвеєр CI зелений.

**Умови злиття** (забезпечено технічно через ruleset `main-protection`):

- ≥1 схвалення;
- усі обговорення закриті;
- CI-перевірка `build` пройдена;
- схвалення анулюються при надходженні нових комітів.

## 5. Мітки

| Мітка | Призначення |
|---|---|
| `bug` | Дефект у наявній функціональності |
| `enhancement` | Нова функція або покращення |
| `documentation` | Документація й артефакти `docs/` |
| `scope` | Відкрите питання щодо меж проєкту |
| `question` | Потребує рішення команди |
| `blocked` | Заблоковано іншим завданням |
| `lab01`…`lab10` | Прив'язка до лабораторної роботи |

Мітки `lab01`…`lab10` створюємо за потреби, а не всі наперед.

| `feedback` | Зворотний зв'язок викладача (мітку ставить викладач) |

## 6. Визначення готовності (Definition of Done)

Зміна готова, коли виконано **все** нижче:

- [ ] Pull Request змерджено в `main` через огляд.
- [ ] CI зелений.
- [ ] Пов'язана issue закрита.
- [ ] Документ у `docs/`, якого стосується зміна, оновлено в тому самому PR.
- [ ] Автор здатен пояснити кожен рядок зміни усно.

Для змін коду діє повний перелік — [статут](TeamCharter.md) §11.4: форматування, лінтер,
аналізатор безпеки, тести й докстрінги.

## 7. Використання ШІ

Використання інструментів ШІ дозволене й очікуване
([політика курсу](https://ssdm-2026.cs-courses.org/ai-policy.html)). Обов'язкові умови:

- **Розкриття:** у кожному PR заповнюється розділ про використання ШІ.
- **Верифікація:** згенерований код читається автором перед комітом і проходить ті самі
  огляд, тести й статичний аналіз, що й написаний вручну.
- **Відповідальність:** автор відповідає за кожен рядок, який здає, незалежно від того, хто
  його написав.
- Неперевірений згенерований код у `main` не потрапляє.

Детальні правила — у [статуті](TeamCharter.md), розділ 8.
