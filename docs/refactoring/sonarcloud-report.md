## 2. Три показники, які покращуємо

Security Rating фіксуємо завжди й у ці три не рахуємо.

Складність вибору в тому, що **чотири з п'яти показників уже на підлозі**:
Code Smells = 0, Maintainability = A, Technical Debt = 0, Duplications = 0.0 %.
Покращувати там нíчого. Єдиний показник із реальним запасом — Reliability Rating.

**Обрано:**

1. **Reliability Rating: E → A.** Дві знахідки, 15 хв зусиль за оцінкою Sonar.
2. **Code Smells: 0 → 0.** Ціль — утримати нуль, перебудувавши 5 файлів.
   Перевірка не формальна: Quality gate на New Code падає від першої ж нової
   проблеми супроводжуваності в зміненому коді.
3. **Technical Debt: 0 хв → 0 хв.** Те саме; обрано замість Duplicated Lines,
   бо саме борг у хвилинах названо метою етапу 2.

**Заміна для показника, якого панель не дає.** Умова етапу 2 передбачає цей
випадок: якщо панель показує менше проблем супроводжуваності, решту добирають
самі — «найскладнішу за Cognitive Complexity функцію». Саме це й зроблено:
`search_free` з когнітивною складністю **23** (§5.1), виміряно локально.
Це і є третій реальний вимір покращення поруч із Reliability Rating.

## 3. Security Rating: E

Рейтинг E означає щонайменше одну знахідку рівня Blocker. Нижче — всі п'ять
знахідок безпеки й надійності з розбором: що це насправді й що з цим робимо.

### 3.1 Що саме знижує рейтинги

| # | Файл : рядок | Знахідка | Якість / Рівень | Оцінка Sonar |
|---|---|---|---|---|
| 1 | `src/api/errors.py:101` | Bearer-токен має бути відкликаний і прибраний з коду | Security / **Blocker** | 30 хв |
| 2 | `src/api/main.py:70` | Прибрати неочікуваний іменований аргумент `summary` | Reliability / **Blocker** | 10 хв |
| 3 | `scripts/check_architecture.py:162` | Command Argument Injection через CLI-аргументи | Security / High | 30 хв |
| 4 | `src/api/openapi_export.py:71` | Path Traversal через CLI-аргументи | Security / High | 30 хв |
| 5 | `docs/.../validation/adr-002/verify_additional.py:188` | `assert` усередині `try/except AssertionError` | Reliability / High | 5 хв |

Ще 2 знахідки безпеки рівня Low на рейтинг не впливають (рейтинг визначає
найгірша знахідка).

### 3.2 Розбір і рішення

**№1 — `errors.py:101`, Security Blocker. Хибне спрацювання; ризик уже закрито.**
Рядок — це поле `action` у `ErrorSpec` для `AUTH_REQUIRED`: текст підказки
користувачу «передайте демо-токен: `Authorization: Bearer demo-student`».
Це не сховище облікових даних, а речення документації. Сам ризик демо-токенів —
це **V-01** з Лаб 5 (`docs/code-quality/static-analysis.md` §5, CWE-1188 +
CWE-798, STRIDE: Elevation of Privilege), і його вже виправлено: у
`src/api/config.py:59` демо-автентифікація вимкнена за замовчуванням
(`_flag("UNISLOT_DEMO_AUTH", default=False)`), а регресійний тест
`tests/api/test_platform.py::test_demo_auth_is_off_unless_enabled` доводить, що
сервер без цієї змінної відповідає 401 навіть на `demo-admin`.
**Дія:** позначити в Sonar як False Positive з обґрунтуванням і посиланням на
V-01, `config.py:59` і цей тест. Потрібні права адміністратора проєкту.

**№2 — `main.py:70`, Reliability Blocker. Хибне спрацювання, перевірено.**
Sonar стверджує, що `fastapi.openapi.utils.get_openapi()` не приймає аргумент
`summary`. Перевірка на закріпленій версії:

```
>>> import inspect; from fastapi.openapi.utils import get_openapi
>>> inspect.signature(get_openapi).parameters["summary"]
summary: str | None = None        # fastapi 0.143.1
```

Аргумент існує. Непряме підтвердження: якби його не було, `get_openapi()`
кидав би `TypeError`, і крок CI `export_openapi.py --check` не проходив би —
а він проходить. Причина спрацювання — аналізатор не бачить залежностей
проєкту під час сканування й бере застарілу сигнатуру.
**Дія:** задати `sonar.python.version` (§3.4) і позначити як False Positive.

**№3 — `check_architecture.py:162`, Security High. Чесно: варто посилити, а не відхиляти.**
`args.plantuml` потрапляє в `subprocess.run(["java", "-jar", args.plantuml, …])`.
Shell не використовується, тож класичної shell-ін'єкції немає, і на це вже
стоїть придушення `# nosec B603 B607` з Лаб 5. Але аргумент — це шлях до jar,
який **виконується**: той, хто керує значенням, запускає довільний код. У CI
jar перевіряється за SHA-256, у локальному запуску — ні. Правило націлене саме
на сценарій, де аргументи постачає агент, а проєкт має власний MCP-сервер
(`src/api/mcp_server.py`), тож сценарій не гіпотетичний.
**Дія:** перевіряти, що шлях існує, це файл і він має розширення `.jar`;
окремий PR `fix:`, не частина рефакторингу Лаб 8.

**№4 — `openapi_export.py:71`, Security High. Те саме, слабший вплив.**
`--out-dir` потрапляє в `mkdir(parents=True)` і `write_text()`. Це
інструмент розробника, а не мережевий маршрут, але запис за довільним шляхом
поза репозиторієм — реальна дія.
**Дія:** звести шлях через `Path.resolve()` і переконатися, що він усередині
кореня репозиторію; той самий PR, що й №3.

**№5 — `verify_additional.py:188`, Reliability High. Поза межами продукту.**
Це заморожений доказ спайка ADR-002 з Лаб 3: код збережено дослівно таким,
яким його запускали, і `pyproject.toml` уже виключає `docs/architecture/validation`
з перевірок Ruff. Sonar про це виключення не знає й сканує каталог.
**Дія:** узгодити область аналізу Sonar з тією, яку проєкт уже оголосив (§3.4).
Правити заморожений доказ не можна — він втратить сенс як доказ.

### 3.3 Зв'язок із Лаб 3 і Лаб 5

Модель загроз STRIDE (`docs/architecture/threat-model.md`) дала перелік того,
чого боїмося. Аналізатор безпеки Лаб 5 (Bandit, pip-audit, detect-secrets) дав
автоматичну перевірку частини з цього — і, як зафіксовано у V-01, **пропустив**
головну знахідку, яку знайшов ручний огляд. Sonar тепер дає третю, незалежну
думку й підсвічує те саме місце з іншого боку. Висновок, який варто назвати на
захисті: три інструменти з різними хибними спрацюваннями й хибними негативами
доповнюють один одного, і жоден сам по собі не є достатнім.

### 3.4 Корінь двох із п'яти знахідок — конфігурація аналізу

Проєкт аналізується в режимі Automatic Analysis, і в репозиторії немає файлу
налаштувань. Через це Sonar не знає ні версії Python, ні того, які каталоги —
не продуктовий код.

Важлива деталь: Automatic Analysis **ігнорує** `sonar-project.properties`;
потрібен файл `.sonarcloud.properties` у корені гілки за замовчуванням.
Підтримуються, зокрема, `sonar.sources`, `sonar.exclusions`, `sonar.tests`,
`sonar.test.exclusions`, `sonar.cpd.exclusions`, `sonar.sourceEncoding`,
`sonar.python.version`. Ті самі значення можна задати в UI
(Administration → General Settings → Analysis Scope → Files); якщо задано
обидва, файл має пріоритет. Документація також зазначає, що шаблони з
підстановними символами не дозволені, тож пишемо прості шляхи й перевіряємо
результат наступним аналізом.

## 5. Запахи коду й рефакторинги (етап 2)

Оскільки панель показує 0 проблем супроводжуваності, запахи дібрано самостійно,
як передбачає умова етапу 2. Для кожного: техніка з каталогу, що лишається
незмінним, що змінюється в структурі, який тест це доводить.

### 5.1 `search_free` — Long Method + Complex Conditional

- **Де:** `src/api/stubs/slot_service.py`
- **Запах:** одна функція тримає перевірку дати, декодування курсора, п'ять
  фільтрів поспіль, сортування й нарізання сторінки. Когнітивна складність
  **23** — понад поріг правила Sonar S3776 (15). Правило не спрацювало лише
  тому, що Sonar не аналізував цей код із потрібними налаштуваннями.
- **Техніка:** **Extract Method** ×3 (`_matches_filters`, `_is_after_cursor`,
  `_cut_page`) + **Decompose Conditional** у фільтрі місткості.
- **Що лишається незмінним:** набір і порядок результатів пошуку; семантика
  кожного фільтра; формат курсора; умова наявності наступної сторінки;
  порядок обчислень (пошук ресурсу досі відбувається до перевірки `is_free`).
- **Що змінюється в структурі:** тіло циклу стає трьома іменованими
  вартовими; «що таке відповідний слот», «що таке після курсора» і «як
  нарізати сторінку» — три окремі рішення з власними назвами й докстрінгами.
- **Який тест це доводить:**
  `tests/unit/test_slot_service.py::test_capacity_filter_excludes_consultations`,
  `::test_cursor_pages_do_not_repeat_when_slot_becomes_occupied`,
  `::test_tied_times_use_uuid_as_tiebreaker`, плюс `tests/api/test_slots.py`.
- **Виміряно:** когнітивна 23 → **10**; циклематична 19 → **8**.

### 5.2 Duplicated Code — п'ять копій конструкції помилки 422

- **Де:** `src/api/pagination.py`, `src/api/stubs/resource_service.py` (×3),
  `src/api/stubs/booking_service.py`
- **Запах:** у п'яти місцях вручну зібрано той самий `ApiProblem` з
  `errors=[{"field": …, "type": …, "message": …}]`. Форма відповіді помилки —
  частина контракту DD-07, і зараз її охороняє лише дисципліна автора. Порядок
  ключів у словнику вже встиг розійтися між файлами.
  Чому Duplications = 0.0 %: детектор Sonar рахує збіги приблизно від 100
  токенів, а ці блоки коротші. Дублювання реальне, але нижче порога — ще одна
  причина не покладатися на один інструмент.
- **Техніка:** **Extract Method** (конструктор `validation_problem()` у
  `src/api/errors.py` — там, де живе модель помилок).
- **Що лишається незмінним:** тіло кожної з п'яти відповідей, байт у байт.
  Ключі `errors[]` і так нормалізує модель `FieldError`, тому різний порядок у
  словниках ніколи не був видимий клієнту.
- **Що змінюється в структурі:** форма `errors[]` описана в одному місці;
  виклик стає одним рядком із чотирма іменованими аргументами замість
  11-рядкового літерала.
- **Який тест це доводить:**
  `tests/unit/test_cursor_validation.py::test_invalid_cursor_shapes_become_validation_problem`,
  `::test_non_json_cursor_is_validation_problem`;
  `tests/unit/test_resource_service.py::test_service_boundary_rejects_invalid_capacity_without_http`;
  `tests/api/test_contract.py`; і найсильніше —
  `python scripts/export_openapi.py --check`: згенерована специфікація не
  змінилася, тобто контракт API ідентичний.
- **Виміряно:** 5 місць збирання помилки поля → **1**.

### 5.3 `update_resource` — Long Method з вкладеними умовами

- **Де:** `src/api/stubs/resource_service.py`
- **Запах:** три перевірки місткості, вкладені в перевірку «чи передано
  capacity», і кожна розгортає власний літерал помилки. Когнітивна складність **11**.
- **Техніка:** **Extract Method** ×2 (`_check_capacity_presence`,
  `_check_capacity_range`), поверх §5.2.
- **Що лишається незмінним:** **порядок перевірок** — наявність місткості,
  потім провайдер, потім межі місткості. Це не косметика: якщо запит ламає
  кілька правил одразу, клієнт отримує саме першу за цим порядком помилку.
  Саме тому витягнуто дві функції, а не одну: одна функція змусила б
  перенести перевірку провайдера й змінила б видиму поведінку.
- **Що змінюється в структурі:** тіло `update_resource` стає послідовністю
  трьох іменованих перевірок; зафіксований порядок описано в докстрінгу.
- **Який тест це доводить:**
  `tests/unit/test_resource_service.py::test_invalid_update_does_not_partially_rename`,
  `::test_consultation_explicit_null_capacity_is_allowed`,
  `::test_service_boundary_rejects_invalid_capacity_without_http`;
  `tests/api/test_resources.py`.
- **Виміряно:** когнітивна 11 → **4**.

### Краєві випадки й припущення

- `_cut_page` при `limit = 0` впаде на `page[-1]`. Так само падав і код до
  рефакторингу; через API це недосяжно (`Limit` має `ge=1`). Поведінку
  **свідомо не змінено**: виправлення дефекту — не рефакторинг.
- `_matches_filters` отримує `resource` аргументом, а не шукає його сам:
  інакше змінився б порядок звернень до сховища.
- Рефакторинг §5.1–5.3 **не впливає** на жодну з п'яти знахідок §3: вони в
  інших файлах або знімаються конфігурацією. Це свідомий поділ: Лаб 8 — про
  поведінково-нейтральну зміну структури, а виправлення знахідок змінює
  поведінку і йде окремими PR.
