## 1. Контекст системи

| Учасник або система | Роль щодо UniSlot | Канал |
|---|---|---|
| Студент | шукає вільні слоти, бронює, скасовує й переносить власні бронювання | браузер → REST API |
| Провайдер | публікує разові слоти й щотижневий шаблон, блокує час | браузер → REST API |
| Адміністратор | керує ресурсами, ролями, політиками; читає журнал аудиту | браузер → REST API |
| Провайдер доставки сповіщень | доставляє повідомлення; у семестрі — заглушка (C-002) | інтерфейс `NotificationGateway` |
| Оператор (команда SSDM_12) | розгортає й супроводжує систему | SSH, Docker Compose (C-005) |

Інтеграції з інформаційними системами НаУКМА й зовнішніми календарями — поза обсягом
(`requirements.md` §1.2), тому в контексті їх немає.

## 2. Архітектурні драйвери

Архітектуру найсильніше визначають нефункціональні вимоги й обмеження: функціональні
вимоги задають, **які** модулі потрібні, а NFR — **як** їх поєднати.

| Драйвер | Що вимагає від архітектури | Відповідь архітектури |
|---|---|---|
| REL-001, FR-032 | сильна узгодженість: не більше одного чинного бронювання на слот навіть за одночасних запитів | одна транзакційна БД, інваріанти в PostgreSQL ([ADR-002](decisions/ADR-002.md)); моноліт без розподілених транзакцій ([ADR-001](decisions/ADR-001.md)) |
| REL-002, FR-053 | бронювання не чекає на доставку сповіщень і не втрачає їх | transactional outbox + окремий worker ([ADR-003](decisions/ADR-003.md)) |
| PERF-001 | пошук на горизонті A-001 серед 5 000 слотів, p95 ≤ 400 мс | матеріалізовані слоти й індекси (DD-02, DD-12) |
| PERF-002 | бронювання під конкуренцією, p95 ≤ 600 мс | короткі транзакції READ COMMITTED з блокуванням рядків, без SERIALIZABLE (ADR-002) |
| SEC-001…SEC-005 | автентифікація, розмежування прав, приватність, підзвітність | окремі модулі `Auth` і `Audit`; deny-by-default; аудит у тій самій транзакції (DD-06, DD-08) |
| MAINT-001 | доменний модуль бронювання покривається тестами ≥ 70% | шари; домен без залежностей від FastAPI і SQLAlchemy; абстракція часу (DD-01, DD-11) |
| USAB-001 | кожна відмова пояснює причину й дію | єдина модель помилок RFC 9457 з полем дії (DD-07) |
| PORT-001 | запуск однією командою `docker compose up` | один образ, міграції як одноразовий контейнер (DD-10) |
| C-001 | стек зафіксовано: Python 3.12, FastAPI, PostgreSQL 16 | стиль і рішення в межах стеку |
| C-002 | реальної доставки немає | адаптер за інтерфейсом `NotificationGateway` із заглушкою |
| C-004, C-005 | ≈ 7 год на тиждень на людину; локальне демо | стиль низької складності, один хост із Docker Compose |
| A-007 | час зберігається в UTC, шаблони задаються в `Europe/Kyiv` | генерація слотів у київському часі з переведенням у UTC (DD-02, DD-11) |

## 3. Архітектурний стиль

**Рішення ([ADR-001](decisions/ADR-001.md)):** UniSlot — **модульний моноліт** з
**багатошаровою** організацією всередині, розгорнутий у **трирівневій клієнт-серверній**
топології; сповіщення — **асинхронно** через outbox і worker.

Реальні системи поєднують стилі (Лекція 3, §2). У UniSlot кожен стиль відповідає за свій
рівень:

| Рівень | Стиль | Навіщо саме тут |
|---|---|---|
| Топологія | клієнт-сервер, трирівнева: браузер → API → БД | контроль і безпека на сервері; REST API — єдина точка входу (`requirements.md` §1.2) |
| Усередині бекенду | багатошарова: presentation → application → domain → infrastructure | розділення відповідальностей; домен тестується без БД і HTTP (MAINT-001) |
| Організація коду | модульний моноліт: модулі за функціями F1–F7 | межі для паралельної роботи команди; модуль можна винести, якщо колись знадобиться (Лаб 8) |
| Сповіщення | елемент керованої подіями архітектури: outbox + worker | бронювання не залежить від доступності доставки (REL-002) |

**Чому не мікросервіси й не повністю керована подіями архітектура.** За порівнянням із
Лекції 3 обидва стилі мають високу складність, кінцеву узгодженість даних і розраховані на
більшу команду. REL-001 вимагає сильної узгодженості, а команда з чотирьох людей із
C-004 не потягне експлуатацію кількох сервісів і брокера. Повний розбір альтернатив — в
ADR-001.

Діаграми: [`uml/component-overview.puml`](uml/component-overview.puml) (рівень 1 — огляд

Таблиця нижче — **джерело канонічних назв компонентів**: матриця простежуваності й скрипт

| Компонент | Відповідальність | Функції й ключові вимоги | Дані, які компонент записує |
|---|---|---|---|
| `Web UI` | мінімальний вебінтерфейс поверх REST API: форми, списки, показ причин відмов | USAB-001; FR-036, FR-041 | — |
| `REST API` | роутери FastAPI, схеми Pydantic, перевірка автентифікації на кожному запиті, переклад доменних помилок у RFC 9457 | FR-007; SEC-002, SEC-004, USAB-001 | — |
| `Auth` | самореєстрація, вхід і вихід, сесії, хешування паролів, ролі й перевірка прав | F1: FR-001–FR-007; SEC-001, SEC-002 | `app_user`, `user_role`, `session` |
| `Availability` | каталог ресурсів, разові слоти, щотижневі шаблони, генерація слотів на горизонт, блокування часу | F2: FR-010–FR-015; зберігає ресурси для F7 | `resource`, `availability_template`, `slot`, `time_block` |
| `Search` | пошук вільних слотів із фільтрами; лише читання | F3: FR-020–FR-023; PERF-001 | — (читає `slot`, `resource`, `booking`, `time_block`) |
| `Booking` | бронювання, скасування, перенесення, перелік власних бронювань; інваріанти бронювання | F4, F5: FR-030–FR-036, FR-040–FR-045; REL-001, PERF-002, SEC-004 | `booking` |
| `Notifications` | outbox сповіщень, планування й скасування нагадувань, доставка через адаптер із повторними спробами | F6: FR-050–FR-054; REL-002 | `notification` |
| `Admin` | адміністративні сценарії: ресурси й призначення провайдера, ролі, політики бронювання | F7: FR-060–FR-065 | `booking_policy` |
| `Audit` | незмінний журнал адміністративних дій і заборонених спроб; перегляд із фільтрами | F7: FR-066–FR-068; SEC-005 | `audit_log` |
| `Platform` | конфігурація зі змінних середовища, сесія БД і Unit of Work, `Clock`, логування, базові класи помилок | SEC-003, PORT-001, MAINT-001, MAINT-002 | — |
| `Worker` | окремий процес із тим самим кодом: dispatcher сповіщень і щоденне продовження горизонту слотів | FR-012, FR-050, FR-051, FR-053; REL-002 | — (через модулі) |
| `PostgreSQL` | зберігання даних і інваріанти цілісності на рівні БД | FR-011, FR-032, FR-067; REL-001, SEC-005 | — |

**Правило власності даних.** Кожну таблицю записує рівно один модуль; інші модулі
отримують ці дані через його інтерфейс. Виняток — `Search`: він читає таблиці
`Availability` і `Booking` напряму SQL-запитами лише для читання. Виняток свідомий:
пошук — найнавантаженіший запит (PERF-001), а прохід через інтерфейси кількох модулів
додав би зайві звернення до БД. Пошук нічого не записує, тому інваріанти не порушує.

**Чому `Admin` не володіє ресурсами.** Ресурси найчастіше читають `Availability`, `Booking`
і `Search`, тому дані ресурсу лежать у `Availability`. `Admin` — тонкий модуль
адміністративних сценаріїв: змінює ресурси через `ResourceManagement`, ролі — через
`RoleAssignment` і кожну зміну записує в журнал аудиту.

## 5. Інтерфейси між компонентами

### 5.1. Зовнішній інтерфейс: REST API

HTTPS + JSON, префікс `/api/v1`. Автентифікація — cookie сесії (DD-06); запити, що
змінюють стан, додатково несуть заголовок `X-CSRF-Token`. Таблиця — повний перелік груп
ендпоінтів. Реалізовану в Лаб 4 частину описує специфікація, згенерована з коду
(`docs/api/openapi-generated.yaml`); проєктні рішення API й відхилення від цієї таблиці — у
[`docs/api/api-design.md`](../api/api-design.md) §5, атрибути якості — у
[`docs/api/quality-attributes.md`](../api/quality-attributes.md).

| Метод і шлях | Роль | Призначення | Вимоги |
|---|---|---|---|
| `POST /auth/register` | гість | самореєстрація студента | FR-001, FR-002, FR-003 |
| `POST /auth/login`, `POST /auth/logout` | гість / будь-яка | вхід і вихід, видача й відкликання сесії | FR-004, FR-005, FR-006 |
| `GET /auth/me` | будь-яка | поточний користувач і ролі | FR-007 |
| `GET /resources` | будь-яка | каталог ресурсів | FR-021 |
| `GET /slots` | студент | пошук вільних слотів: `provider_id`, `resource_type`, `date`, `min_capacity` | FR-020–FR-023 |
| `POST /resources/{id}/slots` | провайдер ресурсу | разовий слот | FR-010, FR-011 |
| `PUT /resources/{id}/templates/{template_id}` | провайдер ресурсу | створити або змінити щотижневий шаблон | FR-012 |
| `POST /resources/{id}/blocks`, `DELETE /resources/{id}/blocks/{block_id}` | провайдер ресурсу | заблокувати проміжок із причиною; зняти блокування | FR-013, FR-014 |
| `GET /providers/me/calendar` | провайдер | календар і завантаження власних ресурсів | FR-015 |
| `POST /bookings` | студент | забронювати слот | FR-030–FR-035 |
| `GET /bookings/{id}` | студент-власник | деталі бронювання | FR-036, SEC-004 |
| `POST /bookings/{id}/cancel` | студент-власник | скасувати | FR-040–FR-042, FR-045 |
| `POST /bookings/{id}/reschedule` | студент-власник | перенести на інший слот | FR-043–FR-045 |
| `GET /me/bookings` | студент | власні бронювання, активні першими | FR-036 |
| `POST /admin/resources`, `PATCH /admin/resources/{id}` | адміністратор | створити й редагувати ресурс, призначити провайдера | FR-060, FR-061 |
| `PUT /admin/users/{id}/roles/{role}`, `DELETE /admin/users/{id}/roles/{role}` | адміністратор | призначити й зняти роль | FR-062, FR-063 |
| `GET /admin/policies/current`, `PUT /admin/policies/current` | адміністратор | переглянути й змінити політику бронювання | FR-064, FR-065 |
| `GET /admin/audit-log` | адміністратор | журнал аудиту з фільтрами | FR-068 |

**Модель помилок (DD-07).** Усі відмови — `application/problem+json` за RFC 9457:
`type` (стабільний ідентифікатор причини), `title`, `detail` і розширення `action` — що
користувач може зробити далі (USAB-001). Коди: 400/422 — некоректні дані; 401 — немає
сесії; 403 — немає права, зокрема на чужий об'єкт (SEC-002, SEC-004); 404 — об'єкта не
існує; 409 — конфлікт зі станом: слот зайнятий, ліміт вичерпано, вікно скасування минуло;
503 — тимчасова відмова: взаємне блокування транзакцій не зникло після одного повтору
(ADR-002, п. 6), `action` — «спробуйте ще раз».

### 5.2. Внутрішні інтерфейси модулів

Інтерфейси — це Python-протоколи (`typing.Protocol`) у шарі application модуля-постачальника.
Виклики синхронні, у межах однієї транзакції Unit of Work, якщо не сказано інше.

| Інтерфейс | Надає | Використовує | Операції | Семантика |
|---|---|---|---|---|
| `AccessControl` | `Auth` | `REST API` | `current_user()`, `require_roles(...)` | deny-by-default: роутер без явних ролей не реєструється |
| `RoleAssignment` | `Auth` | `Admin` | `grant(user, role)`, `revoke(user, role)`, `has_role(user, role)` | `revoke` відмовляє, якщо знімається роль останнього адміністратора (FR-063) |
| `AvailabilityService` | `Availability` | `REST API` | слоти, шаблони, блокування для провайдера | перевіряє, що ресурс належить провайдеру (FR-007) |
| `ResourceManagement` | `Availability` | `Admin` | `create_resource`, `update_resource`, `assign_provider` | лише для адміністративних сценаріїв |
| `SlotCatalog` | `Availability` | `Booking` | `lock_slot(slot_id)`, `bookability(slot, now)` | блокує рядок слота до кінця транзакції (ADR-002) |
| `BlockImpactPort` | реалізує `Booking` | `Availability` | `cancel_bookings_in(resource, period, reason, actor)` | порт визначено в `Availability` — інверсія залежності, див. нижче |
| `SlotSearch` | `Search` | `REST API` | `find_free(filters, now, page)` | лише читання, пагінація |
| `BookingService` | `Booking` | `REST API` | `book`, `cancel`, `reschedule`, `list_mine`, `get_owned` | перевірка власника всередині сервісу (SEC-004) |
| `PolicyProvider` | `Admin` | `Booking` | `current_policy()` | повертає значення A-002, A-003 і `policy_id` |
| `AdminService` | `Admin` | `REST API` | ресурси, ролі, політики | кожна успішна дія — запис аудиту в тій самій транзакції |
| `NotificationOutbox` | `Notifications` | `Booking` | `enqueue(kind, recipient, payload, scheduled_for)`, `cancel_pending(booking_id, kinds)` | лише вставка й оновлення рядків outbox, без мережевих викликів |
| `Dispatcher` | `Notifications` | `Worker` | `dispatch_due(batch_size)` | вибирає записи `FOR UPDATE SKIP LOCKED`, повторює з експоненційною затримкою (ADR-003) |
| `HorizonJob` | `Availability` | `Worker` | `extend_horizon(today)` | ідемпотентно створює слоти з шаблонів до межі A-001 |
| `NotificationGateway` | заглушка доставки (C-002) | `Notifications` | `send(message)` | тайм-аут на виклик; помилка → повтор, а не втрата |
| `AuditLog` | `Audit` | `Admin`, `Auth` | `record(actor, action, object, before, after, outcome)` | лише додавання записів (FR-067) |
| `AuditQuery` | `Audit` | `REST API` | `search(filters, page)` | лише для адміністратора (FR-068) |
| `UnitOfWork`, `Clock` | `Platform` | усі модулі | транзакція й репозиторії; поточний час | `Clock` підміняється в тестах правил A-001, A-003, A-004, A-006 |
| `SQL` | `PostgreSQL` | `Platform` | SQLAlchemy 2.x + psycopg | параметризовані запити, без склеювання SQL (THR-05) |

**Інверсія залежності між `Availability` і `Booking`.** `Booking` потребує слотів
(`SlotCatalog`), а блокування часу в `Availability` має скасувати бронювання (FR-014).
Прямі виклики в обидва боки дали б циклічну залежність модулів. Тому порт
`BlockImpactPort` оголошено в `Availability`, а реалізує його `Booking`: на діаграмі
`Availability` потребує інтерфейс, `Booking` його надає, а в коді обидві залежності
спрямовані від `booking` до `availability`.

### 5.3. Інтерфейси розгортання

| Звідки → куди | Протокол і порт | Межа довіри |
|---|---|---|
| браузер → `proxy` (nginx) | HTTPS 443 | TB1 |
| `proxy` → `api` | HTTP 8000, мережа `edge` | TB2 |
| `api`, `worker`, `migrate` → `db` | SQL, TCP 5432, мережа `backend` | TB3 |

| оператор → сервер | SSH, Docker Compose | TB5 |

Межі довіри TB1–TB5 розібрано в [`threat-model.md`](threat-model.md).

## 6. Шари й правило залежностей

Кожен модуль має чотири шари:

| Шар | Що в ньому | Від чого може залежати |
|---|---|---|
| `api` (presentation) | роутери FastAPI, схеми Pydantic | `application` свого модуля, `AccessControl` |
| `application` | сценарії використання, межі транзакцій, інтерфейси модуля | `domain`, інтерфейси інших модулів, `UnitOfWork`, `Clock` |
| `domain` | сутності, правила, доменні помилки; чистий Python | нічого, крім стандартної бібліотеки |
| `infrastructure` | репозиторії SQLAlchemy, адаптери (Argon2id, заглушка доставки) | `domain`, `Platform` |

Правила:

1. Залежності спрямовані лише згори вниз; з базою даних розмовляє тільки шар
   `infrastructure`.
2. Модуль звертається до іншого модуля лише через його інтерфейс із §5.2, не до
   репозиторіїв і моделей чужого модуля.
3. Граф залежностей модулів ациклічний: `Booking` → `Availability`, `Admin`,
   `Notifications`; `Admin` → `Availability`, `Auth`, `Audit`; `Auth` → `Audit`.

**Структура пакетів** (каркас створено в Лаб 5; REST API лишився пакетом `src/api/` — AQ-08):

```text
src/unislot/
├── api/                 # застосунок FastAPI, підключення роутерів, обробники помилок
├── auth/                # api/ application/ domain/ infrastructure/
├── availability/
├── search/
├── booking/
├── notifications/
├── admin/
├── audit/
├── platform/            # config, db (Unit of Work), clock, logging
└── worker.py            # точка входу процесу Worker
```

Дотримання правил перевіряє import-linter у CI (`.importlinter`) — fitness-функція
архітектури (Лекція 3, §4–§5). З Лаб 5 діють два контракти: модулі `unislot` не імпортують
пакет `api`; доменні шари й `unislot.platform.errors` не імпортують FastAPI, Starlette,
Pydantic і SQLAlchemy. Контракт шарів усередині модуля (правило 1 повністю) і контракт
інтерфейсів між модулями (правило 2) додаємо, коли модуль отримує шари `application` і
`infrastructure`.

## 8. Розгортання

Діаграма: [`uml/deployment.puml`](uml/deployment.puml) — цільове виробниче середовище з
межами довіри. Локальне демо (C-005) використовує той самий `docker-compose.yml`.

| Контейнер | Образ | Призначення | Мережі | Порти назовні |
|---|---|---|---|---|
| `proxy` | nginx | TLS, редирект HTTP → HTTPS, заголовки HSTS і CSP, обмеження частоти запитів | `edge` | 443 (і 80 для редиректу) |
| `api` | `unislot` | uvicorn + FastAPI; віддає також статику Web UI | `edge`, `backend` | — |
| `worker` | `unislot` | `python -m unislot.worker`: dispatcher і продовження горизонту | `backend` | — |
| `migrate` | `unislot` | `alembic upgrade head`; завершується до старту `api` і `worker` | `backend` | — |
| `db` | `postgres:16` | дані, том `pgdata` | `backend` (internal) | — |

**Порядок старту:** `db` (healthcheck готовності) → `migrate` (успішне завершення) →
`api`, `worker` → `proxy`. Так `docker compose up` на чистій машині без ручних кроків
піднімає робочу систему (PORT-001).

**Конфігурація й секрети (DD-09).** Пароль БД та інші секрети — лише в `.env` на хості;
`.env` уже виключено в `.gitignore`, у репозиторії лежить `.env.example` без значень.

**Масштабування.** Цільове навантаження (PERF-001: 50 одночасних користувачів;
PERF-002: 100 одночасних запитів) обслуговує один екземпляр `api`. Якщо вимір у Лаб 6
покаже інше, `api` масштабується горизонтально без змін коду: стан сесій у БД, а
інваріанти тримає PostgreSQL. Єдина точка відмови — один хост і одна БД — прийнята для
навчального розгортання (C-005).

## 9. Наскрізні аспекти

- **Час (A-007).** Усі моменти часу — `timestamptz` в UTC. Шаблони доступності задаються в
  `Europe/Kyiv`; слоти генеруються з них через базу часових поясів `zoneinfo`, тож під час
  сезонного переходу локальний час слота не змінюється, а UTC зсувається (TC-031). Дати
  переходів беруться з tzdata, а не з коду. Неіснуючий локальний час весняного переходу
  пропускається, неоднозначний осінній береться в першому входженні (`fold=0`).
- **Транзакції й узгодженість.** Межа транзакції — один сценарій використання в шарі
  `application`. Порядок блокувань в усіх сценаріях однаковий — студент → слоти за
  зростанням часу → бронювання, — щоб уникнути взаємних блокувань (ADR-002).
- **Безпека.** Автентифікація сесією з непрозорим токеном (DD-06); перевірка ролі на
  кожному запиті й перевірка власника в сервісах; явні схеми вводу (`extra="forbid"`);
  параметризовані запити; аудит адміністративних дій (DD-08); секрети поза репозиторієм
  (DD-09). Повний аналіз — у [`threat-model.md`](threat-model.md).
- **Помилки.** Доменні помилки — окремі класи (`SlotAlreadyBooked`, `BookingLimitReached`,
  `CancellationDeadlinePassed` тощо). `REST API` перекладає їх у RFC 9457 з полем `action`
  (DD-07), тож тексти відмов живуть в одному каталозі й перевіряються за USAB-001.
- **Логування.** Структуровані логи з ідентифікатором запиту; паролі, токени й тексти
  сповіщень у логи не потрапляють (THR-02, THR-09).
- **Тестованість.** Домен не імпортує FastAPI і SQLAlchemy; час — через `Clock`;
  інтеграційні тести працюють зі справжнім PostgreSQL у Docker, бо REL-001 недоказова
  без реальних транзакцій (`Project-Description.md` §2.6).
