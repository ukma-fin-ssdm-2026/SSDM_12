# Architecture Decision Records (ADR) — UniSlot

ADR фіксує одне архітектурне рішення: контекст (які вимоги тиснуть), рішення, наслідки й
відхилені альтернативи. Пишемо для колеги, який відкриє репозиторій через пів року й
спитає «чому саме так?».

| ADR | Рішення | Статус | Автор |
|---|---|---|---|
| [ADR-001](ADR-001.md) | Архітектурний стиль: модульний моноліт із шарами в клієнт-серверній топології | Прийнято (09.10.2026) | @NykytaBabakov |
| [ADR-002](ADR-002.md) | Відсутність подвійних бронювань гарантує PostgreSQL: частковий унікальний індекс і блокування рядків | Прийнято (12.10.2026, PR #91) | @dysett |
| [ADR-003](ADR-003.md) | Сповіщення через transactional outbox у PostgreSQL і окремий worker | Прийнято (09.10.2026, архітектурна сесія) | @NykytaBabakov |

Менші рішення без окремого ADR — у таблиці DD-01…DD-16 у
[`high-level-design.md`](../high-level-design.md) §10.

## Правила

- Файл `ADR-NNN.md`, номери наскрізні й не перевикористовуються.
- Статуси: **Запропоновано** → **Прийнято** (дата й де ухвалено) → за потреби
  **Замінено ADR-NNN**. Прийняте ADR по суті не переписуємо: якщо рішення змінилося,
  пишемо нове ADR і в старому ставимо статус «Замінено».
- ADR без відхилених альтернатив — не ADR: кожне має щонайменше дві альтернативи з
  причиною відмови.
- Технічні розбіжності, що переживають тиждень, оформлюються як ADR (статут, розділ 5).

## Шаблон

```markdown
# ADR-NNN: <рішення одним реченням-назвою>

- **Статус:** Запропоновано (<дата>)
- **Автор:** @<нік> · **Рецензенти:** @<нік>
- **Пов'язані вимоги:** <FR-…, NFR-…, C-…>

## Контекст
Які вимоги й обмеження тиснуть на рішення; що станеться, якщо нічого не вирішувати.

## Рішення
Одне стверджувальне речення, далі — деталі, без яких рішення не реалізувати.

## Наслідки
- **Позитивні:** …
- **Застереження:** …
- **Негативні:** …

## Розглянуті альтернативи
| Альтернатива | Чому відхилено |
|---|---|

## Як перевіримо
Тест, метрика або fitness-функція, що покаже, чи рішення працює.
```
