# ADR-002: Відсутність подвійних бронювань гарантує PostgreSQL — частковий унікальний індекс і блокування рядків

- **Статус:** Прийнято (12.10.2026, схвалений PR #91).
- **Автор:** @dysett · **Рецензенти:** @DziubakPavlo, @NykytaBabakov
- **Пов'язані вимоги:** REL-001, PERF-002; FR-011, FR-014, FR-032, FR-033, FR-035, FR-043, FR-044

## Контекст

- **REL-001:** зі 100 одночасних запитів на один вільний слот рівно один завершується
  кодом 201, решта — 409; подвійних бронювань 0.
- Інші правила, які змагаються з бронюванням за ті самі дані:
  - ліміт активних бронювань студента A-002 (FR-033) і заборона перетину з власним
    бронюванням (FR-035) — це правила над **кількома** рядками;
  - слоти одного ресурсу не перетинаються (FR-011);
  - блокування проміжку скасовує бронювання й робить слоти недоступними (FR-014):
    бронювання, яке комітиться одночасно з блокуванням, не повинне «вижити»;
  - перенесення — атомарна заміна (FR-043, FR-044).
- **PERF-002:** p95 ≤ 600 мс за 100 одночасних запитів на різні слоти — транзакції мають
  бути короткими, а блокування — вузькими.
- Типова помилка — «перевірити, потім вставити» (check-then-act) у коді: дві транзакції
  одночасно бачать слот вільним і обидві вставляють бронювання.
- PostgreSQL обрано замість SQLite саме заради справжніх транзакцій
  (`Project-Description.md` §2.6, C-001).

## Рішення

**Інваріант «не більше одного чинного бронювання на слот» тримає частковий унікальний
індекс PostgreSQL, а правила над кількома рядками — блокування рядків `SELECT … FOR UPDATE`
у транзакції READ COMMITTED з однаковим порядком блокувань; конфлікт повертається
клієнтові як 409.**

Деталі:

1. **Унікальність чинного бронювання:**
   `CREATE UNIQUE INDEX uq_booking_slot_confirmed ON booking (slot_id) WHERE status = 'confirmed';`
2. **Слоти ресурсу не перетинаються** (розширення `btree_gist`):
   `ALTER TABLE slot ADD CONSTRAINT ex_slot_no_overlap EXCLUDE USING gist (resource_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&);`
   Діапазон `[)` — це півінтервал із глосарію: суміжні слоти дозволені (TC-026).
3. **Транзакція бронювання:** блокування рядка студента → блокування рядка слота →
   перевірки (A-001, A-006, немає активного блокування й чинного бронювання, ліміт A-002,
   перетин FR-035) → `INSERT booking` → записи outbox → `COMMIT`.
4. **Транзакція блокування часу (FR-014):** блокування рядків слотів ресурсу в проміжку
   за зростанням часу → `INSERT time_block` → скасування чинних бронювань у проміжку →
   записи outbox → `COMMIT`. Одночасне бронювання чекає на блокування рядка слота, а
   після нього бачить новий `time_block` і отримує відмову.
5. **Перенесення:** блокування рядка студента → блокування старого й нового слотів за
   зростанням часу → генерація UUID наступника → старе бронювання одним `UPDATE` стає
   скасованим (`rescheduled`) із `rescheduled_to_id` → вставка нового з цим UUID →
   перепланування нагадування → `COMMIT`. Будь-яка помилка → `ROLLBACK`, старе бронювання
   лишається чинним.
   FK `rescheduled_to_id → booking.id` має бути `DEFERRABLE INITIALLY DEFERRED`, щоб
   існування наступника перевірялося під час `COMMIT`; `UNIQUE (rescheduled_to_id)`
   забезпечує не більше одного попередника. Це дозволяє виконати `CHECK` INV-14
   при скасуванні старого запису до вставки нового.
6. **Порядок блокувань всюди однаковий:** студент → слоти (за `starts_at`, далі `id`) →
   бронювання. Якщо PostgreSQL усе ж виявить взаємне блокування (SQLSTATE `40P01`),
   після `ROLLBACK` повторюється вся транзакція один раз; після повторного `40P01` —
   відповідь 503 «спробуйте ще раз». Продовжувати окремий SQL-запит у вже перерваній
   транзакції не можна. Зовнішня доставка сповіщень виконується після коміту через outbox.
7. **Переклад помилок БД:** `23505` на `uq_booking_slot_confirmed` → `SlotAlreadyBooked`
   (409); `23P01` на `ex_slot_no_overlap` → `SlotOverlap` (409).

## Наслідки

- **Позитивні:**
  - Гарантія не залежить від того, яким шляхом код записує бронювання і скільки
    екземплярів `api` працює: арбітр один — база даних.
  - Декларативно й перевірювано: обмеження має створювати міграція; заплановані
    TC-004 і TC-062 мають перевірити поведінку застосунку.
  - READ COMMITTED із блокуванням рядків дозволяє запитам до різних студентів і слотів
    виконуватися паралельно; цільову затримку задає PERF-002.
- **Застереження:**
  - Порядок блокувань — дисципліна коду; пункт у чек-листі рев'ю, повтор після `40P01`.
  - Частковий індекс, `EXCLUDE` і `btree_gist` — можливості саме PostgreSQL; прив'язку до
    СУБД прийнято (C-001).
  - Рішення потребує реальних рядків слотів, тому слоти матеріалізуються (DD-02).
- **Негативні:**
  - Одночасні запити одного студента виконуються по черзі та чекають на звільнення
    блокування його рядка.
  - Інтеграційні тести потребують справжнього PostgreSQL у Docker — вони повільніші за
    модульні.

## Розглянуті альтернативи

| Альтернатива | Чому відхилено |
|---|---|
| Перевірка в коді без обмеження в БД («перевірити, потім вставити») | Гонка check-then-act: дві транзакції бачать слот вільним — REL-001 порушено. |
| SERIALIZABLE для всіх транзакцій бронювання з повтором після `40001` | Потребує обробки serialization failure й повтору всієї транзакції. Для відомих конфліктів обрано явний порядок блокувань і декларативні обмеження; SERIALIZABLE лишається запасним варіантом. |
| Оптимістичне блокування: стовпець `version` у `slot` | Для одного слота ефект той самий, але більше коду; ліміт студента й FR-014 однаково потребують окремих перевірок. |
| Розподілений замок у Redis | Ще один компонент для розгортання й підтримки (C-004, PORT-001); замок не атомарний із `COMMIT` у PostgreSQL. |
| Усі бронювання через одну чергу й один обробник | Студент отримує «запит прийнято» замість 201 або 409 одразу (US-001); одна черга — вузьке місце продуктивності. |

## Як перевіримо

**Виконаний архітектурний спайк — 12.10.2026.** Codex запустив перевірки на окремому
PostgreSQL 16.15 у Windows 10; Python 3.12.14, psycopg 3.3.6, `max_connections = 200`.
Для конкурентних сценаріїв виконано по 20 прогонів із 100 одночасними SQL-транзакціями.
З'єднання встановлено до старту й синхронізовано бар'єром; винятки потоків передаються
головному потоку, результати й кількість записів перевіряються твердженнями `assert`.

Питання спайку: чи забезпечують індекс і блокування цілісність, а порядок перенесення —
атомарність? Контрольні сценарії навмисно прибирають захист, щоб відтворити гонку.

| Перевірка | Фактичний результат |
|---|---|
| Блокування рядків + перевірка + частковий індекс, 20 × 100 | У кожному прогоні 1 успіх, 99 конфліктів, 1 чинне бронювання на слоті |
| Лише частковий індекс, 20 × 100 | У кожному прогоні 1 успіх, 99 конфліктів, 1 чинне бронювання |
| Контроль check-then-act без індексу й блокувань, 20 × 100 | Від 72 до 100 успіхів на одному слоті — відтворено порушення інваріанта |
| Блокування часу без блокування рядка слота | 1 чинне бронювання лишилося в заблокованому проміжку |
| Блокування часу з блокуванням рядка слота | 0 чинних бронювань; очікування рядкового блокування перевірено через `pg_blocking_pids` |
| `EXCLUDE` для слотів | Перетин відхилено (`23P01`), суміжний слот дозволено |
| Частковий індекс | Друге чинне бронювання відхилено (`23505`); після скасування нове дозволено |
| Незмінність аудиту | `UPDATE` роллю застосунку відхилено (`42501`), `DELETE` власником — тригером (`P0001`); UUIDv4 і тригер для UUID-ключа перевірено окремо |
| `UNIQUE (rescheduled_to_id)` | Другий попередник відхилений (`23505`); кілька `NULL` дозволено |
| `CHECK` для перенесення | Відсутній наступник або невідповідний вид скасування відхилено (`23514`) |
| Відкладений FK наступника | Послідовність «скасувати старе → вставити нове» проходить; відсутній наступник під час `COMMIT` дає `23503` |
| Контроль із негайним FK наступника | Оновлення старого запису до вставки нового відхилено (`23503`) |
| Атомарність перенесення | Зайнята ціль і помилка після вставки нового запису спричиняють повний відкат; старе бронювання збережено |
| Конкурентні перенесення, 20 × 100 | По 1 успіху й 99 конфліктів; 1 чинне бронювання на цілі, усі 99 старих бронювань невдалих перенесень збережено |
| Взаємне блокування та повтор | Спричинено реальний `40P01`; одна транзакція повторилася після відкату; обидві завершилися, у таблиці по одному запису від кожної |

Код, журнали та JSON із результатами кожного прогону збережено у
[`validation/adr-002`](../validation/adr-002/README.md). Це перевірка SQL-моделі й
архітектурного алгоритму; коди `201`/`409` у спайку позначають результат транзакції.
Вимоги до HTTP API й продуктивності перевіряються на рівні застосунку за планом нижче.

**Постійні перевірки реалізації:**

- TC-004: 100 одночасних HTTP-запитів на один слот → рівно один 201, решта 409.
- TC-062: одночасні перенесення й бронювання на той самий цільовий слот.
- TC-061: p95 створення бронювання на різні слоти за умов PERF-002.
- Тест міграції: існують `uq_booking_slot_confirmed`, `ex_slot_no_overlap` і відкладений
  FK `rescheduled_to_id`; повторний запуск міграцій відтворює обмеження моделі.
- Рецензія порядку блокувань у кожній транзакції, яка змінює бронювання.
