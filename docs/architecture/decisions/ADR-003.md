# ADR-003: Сповіщення через transactional outbox у PostgreSQL і окремий worker

- **Статус:** Прийнято (09.10.2026, архітектурна сесія)
- **Автор:** @NykytaBabakov (артефакт передано за §6.1 статуту; початковий виконавець — @DziubakPavlo) · **Рецензент:** @asyakozulina
- **Пов'язані вимоги:** REL-002, PERF-002; FR-050, FR-051, FR-052, FR-053, FR-054; C-002, PORT-001

## Контекст

- **REL-002:** бронювання завершується за ≤ 2 с навіть за недоступного адаптера
  сповіщень; 100% недоставлених сповіщень потрапляють у чергу повторних спроб.
- **FR-050…FR-054:** підтвердження, нагадування за A-004, сповіщення провайдеру, черга
  повторних спроб, перепланування нагадування після перенесення.
- **C-002:** реальної доставки немає — працює заглушка, яку згодом замінять справжнім
  провайдером; заміна не повинна зачепити бізнес-логіку.
- **Проблема подвійного запису:** зберегти бронювання в БД і надіслати повідомлення в
  зовнішню систему атомарно неможливо. Закомітили й упали до надсилання — сповіщення
  втрачено; надіслали, а транзакція відкотилася — студент отримав підтвердження
  неіснуючого бронювання.
- **Лаб 9** вимагатиме ін'єкції збою в адаптер — збій має вмикатися керовано.

## Рішення

**Сповіщення записуються в таблицю `notification` (outbox) у тій самій транзакції, що й
зміна бронювання; окремий процес `Worker` періодично викликає `dispatch_due(batch_size)`
модуля `Notifications`, який вибирає готові записи (`FOR UPDATE SKIP LOCKED`), надсилає їх
через інтерфейс `NotificationGateway` з тайм-аутом і повторює невдалі спроби з
експоненційною затримкою. Нагадування — записи outbox із відкладеним часом `scheduled_for`.**

Деталі:

- Стани запису: `pending` → `sent`; після вичерпання спроб — `failed` (лишається для
  аналізу й ручного повтору); `cancelled` — нагадування скасованого чи перенесеного
  бронювання.
- Затримка між спробами росте експоненційно до верхньої межі; кількість спроб і межі —
  у конфігурації, стартові значення підбираємо в Лаб 9.
- Доставка «щонайменше один раз»: `id` запису — ключ ідемпотентності для провайдера.
- Нагадування: під час бронювання створюється запис на `starts_at − A-004`, якщо цей
  момент ще не настав (A-004); скасування бронювання → `cancel_pending`; перенесення →
  скасування старого й створення нового запису (FR-054).
- Заглушка `NotificationGateway` має режим збою, що вмикається змінною середовища, —
  для тестів REL-002 і Лаб 9.

## Наслідки

- **Позитивні:**
  - Бронювання ніколи не чекає на доставку (REL-002) і не відкочується через неї.
  - Жодне сповіщення не губиться: запис outbox атомарний зі зміною бронювання.
  - Нагадування, їх скасування й перепланування — звичайні операції над рядками.
  - Ін'єкцію збою легко керувати; брокер повідомлень не потрібен (PORT-001).
- **Застереження:**
  - «Щонайменше один раз»: якщо `Worker` впаде між надсиланням і оновленням статусу,
    повідомлення може прийти двічі — тому ключ ідемпотентності.
  - Затримка доставки до інтервалу опитування: «одразу» у FR-050 треба уточнити (AQ-03).
  - Таблиця outbox росте — потрібне очищення старих надісланих записів (AQ-06).
- **Негативні:**
  - Ще один процес, який треба запускати й моніторити.
  - Опитування додає невелике навантаження на БД; індекс за `(status, scheduled_for)`
    тримає його дешевим.

## Розглянуті альтернативи

| Альтернатива | Чому відхилено |
|---|---|
| Синхронний виклик адаптера в запиті бронювання | Недоступний або повільний адаптер затримує чи ламає бронювання — пряме порушення REL-002. |
| `BackgroundTasks` FastAPI або задачі asyncio в процесі `api` | Задачі живуть у пам'яті й зникають під час перезапуску — «100% у черзі» не виконується; повтори не зберігаються. |
| Брокер повідомлень (RabbitMQ або Redis + Celery) | Додаткова інфраструктура й експлуатація (C-004, PORT-001); проблема подвійного запису «БД + брокер» без outbox однаково лишається. |
| `LISTEN/NOTIFY` у PostgreSQL як черга | Повідомлення не зберігаються, якщо слухача немає. Можна додати пізніше лише як сигнал «прокинься» для `Worker`. |

## Як перевіримо

- TC-006, TC-020, TC-024, TC-063 (Лаб 9): заглушка в режимі збою → бронювання завершуються
  за ≤ 2 с, усі сповіщення лишаються `pending`; після відновлення — `sent`.
- TC-016, TC-019 (Лаб 6): перенесення переплановує нагадування, скасування його скасовує.
