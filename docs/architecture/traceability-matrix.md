## Дві матриці — дві ролі

- [`docs/requirements/rtm.md`](../requirements/rtm.md) — реєстр вимог: історія → FR → NFR →
  тест. Оновлюється щоразу, коли змінюється вимога.
- Цей файл — **архітектурний зріз тих самих вимог**: вимога → компонент → проєктне рішення
  → метод верифікації.

Правило перевірки одне: **жодної вимоги без компонента, жодного компонента без вимоги**.
Його механічно перевіряє `scripts/check_architecture.py` (результат — у §6). Назви
компонентів — канонічні, з таблиці `high-level-design.md` §4.

## 4. Сценарії атрибутів якості

Формат — шість частин сценарію атрибута якості (джерело, стимул, артефакт, середовище,
реакція, міра реакції) плюс тактики й метод верифікації. Міра реакції береться з NFR, а не
вигадується заново.

### QAS-01. Продуктивність пошуку (PERF-001)

| Частина | Значення |
|---|---|
| Джерело стимулу | 50 автентифікованих студентів одночасно |
| Стимул | запити пошуку вільних слотів із фільтрами на горизонті A-001 |
| Артефакт | `Search`, `PostgreSQL` (таблиці `slot`, `booking`, `time_block`) |
| Середовище | нормальна робота; локальний Docker Compose; у БД 5 000 слотів і 200 користувачів |
| Реакція | система повертає лише вільні слоти, що відповідають фільтрам |
| Міра реакції | p95 часу відповіді ≤ 400 мс |
| Тактики | матеріалізовані слоти (DD-02); індекс `(resource_id, starts_at)`, пагінація, обмежений горизонт (DD-12) |
| Верифікація | навантажувальний тест Locust — TC-060, Лаб 6; звіт у `docs/testing/` |

### QAS-02. Надійність бронювання під конкуренцією (REL-001)

| Частина | Значення |
|---|---|
| Джерело стимулу | 100 студентів |
| Стимул | одночасні `POST /bookings` на той самий вільний слот |
| Артефакт | `Booking`, `PostgreSQL` |
| Середовище | нормальна робота; PostgreSQL зі справжніми транзакціями |
| Реакція | створюється одне бронювання; решта студентів отримує відмову з поясненням |
| Міра реакції | рівно одна відповідь 201, решта — 409; частка подвійних бронювань — 0 |
| Тактики | частковий унікальний індекс; блокування рядків слота й студента з фіксованим порядком (ADR-002) |
| Верифікація | навантажувальний тест TC-004, Лаб 6; спайк ADR-002 уже показав 1 успіх у кожному з 20 прогонів |

### QAS-03. Безпека: доступ до чужого бронювання (SEC-004, SEC-002)

| Частина | Значення |
|---|---|
| Джерело стимулу | автентифікований студент (цікавий або зловмисний) |
| Стимул | `GET /bookings/{id}` або `POST /bookings/{id}/cancel` з ID бронювання іншого студента |
| Артефакт | `REST API`, `Auth`, `Booking` |
| Середовище | нормальна робота |
| Реакція | відмова в доступі; чужі дані не розкриваються; стан бронювання не змінюється |
| Міра реакції | 100% таких запитів → 403; 0 розкритих полів чужого бронювання; 100% негативних кейсів RBAC-матриці → 403 |
| Тактики | перевірка власника в сервісному шарі; deny-by-default (DD-06); неперебірні UUIDv4 (DD-13) |
| Верифікація | тести безпеки TC-058, TC-065, TC-067, Лаб 6; рев'ю коду з фокусом на THR-03, Лаб 5 |

### QAS-04. Відмовостійкість: недоступний адаптер сповіщень (REL-002)

| Частина | Значення |
|---|---|
| Джерело стимулу | збій зовнішньої залежності |
| Стимул | адаптер сповіщень недоступний (заглушка в режимі збою) у момент бронювання |
| Артефакт | `Booking`, `Notifications`, `Worker` |
| Середовище | деградований режим: доставка не працює |
| Реакція | бронювання створюється; сповіщення накопичуються в outbox і доставляються після відновлення |
| Міра реакції | бронювання завершується за ≤ 2 с; 100% недоставлених сповіщень у черзі повторних спроб |
| Тактики | transactional outbox, тайм-аут, повтори з експоненційною затримкою (ADR-003) |
| Верифікація | ін'єкція збою TC-006, TC-020, TC-024, TC-063, Лаб 9 |
