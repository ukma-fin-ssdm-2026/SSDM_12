## 1. Призначення та межі

UniSlot усуває накладки й загублені домовленості під час запису на консультації
та бронювання аудиторій, замінюючи розрізнені канали єдиним джерелом правди
про зайнятість ресурсу.

### 1.1. Бізнес-потреби

- **BN-001** — Студентові потрібен передбачуваний запис: бачити вільний час, зайняти його без домовлянь у чатах і бути впевненим, що запис не зникне. Пропущені консультації через забуті домовленості мають зникнути як клас.
- **BN-002** — Провайдеру потрібен контроль над власним часом: публікувати доступність один раз на тиждень замість щоденного листування, закривати час, коли він зайнятий, і бачити своє завантаження наперед.
- **BN-003** — Адміністрації потрібні єдиний реєстр ресурсів факультету, керовані правила бронювання й простежуваність адміністративних дій, щоб спірні ситуації розв'язувалися за записами, а не за спогадами.

### 1.2. В обсязі та поза обсягом

**У обсязі цього семестру**

- Автентифікація, самореєстрація студентів і розмежування прав за трьома ролями.
- Публікація доступності: разові слоти та щотижневий повторюваний шаблон; блокування часу.
- Пошук вільних слотів із фільтрами; бронювання, скасування, перенесення.
- Політики бронювання: вікно скасування, ліміт активних бронювань (A-002, A-003).
- Сповіщення через внутрішній адаптер із заглушкою замість реального провайдера доставки.
- Панель адміністратора: ресурси, користувачі, ролі, політики, журнал аудиту.
- REST API як єдина точка входу для всіх операцій.

**Поза обсягом**

- Підтвердження бронювань провайдером — рішення в #9.
- Вікно скасування, налаштовуване на рівні ресурсу — рішення в #10.
- Список очікування на зайнятий слот — рішення в #11.
- Групові бронювання: кілька студентів на один слот.
- Платежі та фінансові операції.
- Нативні мобільні застосунки.
- Інтеграція з інформаційними системами НаУКМА та синхронізація із зовнішніми календарями.
- Чат між учасниками; багатомовність інтерфейсу.
- Правила повторення, складніші за щотижневі.
- Реальна доставка e-mail і SMS.

## 2. Глосарій

Терміни вжито в цьому значенні в усіх файлах `docs/requirements/`.
Якщо термін змінює значення, він змінюється тут, а не в окремому документі.

| Термін | Значення |
|---|---|
| **Ресурс** | Об'єкт, на який записуються: консультація конкретного викладача або навчальна аудиторія. Має назву, тип, провайдера, а для аудиторій — місткість. |
| **Тип ресурсу** | «Консультація» або «аудиторія». Визначає, чи застосовується фільтр за місткістю (FR-022). |
| **Провайдер** | Користувач, відповідальний за ресурс: викладач для своїх консультацій, відповідальний за аудиторію. Публікує доступність і блокує час. |
| **Студент** | Користувач, який шукає й бронює вільні слоти. Роль за замовчуванням для самостійно зареєстрованих облікових записів. |
| **Адміністратор** | Користувач, який керує ресурсами, ролями й політиками та читає журнал аудиту. |
| **Слот** | Проміжок часу на конкретному ресурсі, доступний для бронювання. Задається датою, часом початку й тривалістю (A-005). Півінтервал: кінець слота не належить йому, тому суміжні слоти не перетинаються. |
| **Шаблон доступності** | Щотижневе правило, з якого слоти створюються на горизонт бронювання. Задається в київському часі (A-007). |
| **Блокування** | Проміжок часу, оголошений провайдером недоступним. Наявні бронювання в цьому проміжку скасовуються з причиною (FR-014). |
| **Бронювання** | Запис конкретного студента на конкретний слот. |
| **Активне бронювання** | Бронювання, слот якого ще не почався і яке не скасовано. На один слот їх не більше одного (FR-032). |
| **Завершене бронювання** | Стан бронювання після закінчення слота. Не окрема дія, а наслідок плину часу. |
| **Скасоване бронювання** | Бронювання, скасоване студентом у межах вікна скасування або провайдером через блокування часу. |
| **Горизонт бронювання** | Період наперед, у межах якого видно й можна бронювати слоти (A-001). |
| **Вікно скасування** | Мінімальний час до початку слота, коли студент ще може скасувати або перенести бронювання (A-003). Єдине для всієї системи. |
| **Граничний час скасування** | Конкретний момент, обчислений для окремого бронювання при його створенні як «початок слота мінус вікно скасування». Не змінюється, якщо адміністратор згодом змінить політику (FR-041, FR-065). |
| **Ліміт активних бронювань** | Максимальна кількість активних бронювань одного студента (A-002). |
| **Політика бронювання** | Набір значень, які задає адміністратор: вікно скасування й ліміт активних бронювань. |
| **Сповіщення** | Повідомлення користувачеві про подію: підтвердження, нагадування, скасування. |
| **Адаптер сповіщень** | Внутрішній компонент, через який система надсилає сповіщення. У цьому семестрі має заглушку замість реального провайдера доставки (C-002). |
| **Черга повторних спроб** | Механізм, куди потрапляє недоставлене сповіщення, щоб недоступність адаптера не блокувала бронювання (FR-053, NFR-5). |
| **Журнал аудиту** | Незмінний запис адміністративних дій із ресурсами, ролями й політиками: автор, час, об'єкт, попереднє й нове значення (FR-066, FR-067). |
| **Накладка** | Ситуація, коли на один слот претендують двоє. Усунення накладок — основна причина існування системи (BN-001). |

## 3. Зацікавлені сторони та джерела вимог

## 4. Функціональні вимоги (FR)

Одне твердження — одна вимога. Пріоритети за MoSCoW. Числа не дублюються
в тексті: вимоги посилаються на припущення A-### з §6. Посилання на NFR
подано в нумерації міні-ТЗ §2.5 — після §5 їх замінять на ID за категоріями.

### F1. Автентифікація та авторизація (FR-001…FR-009)

- **FR-001** (Must) — Система повинна дозволяти відвідувачу самостійно зареєструватися, створюючи обліковий запис із роллю «студент». *Джерело:* F1, US-010.
- **FR-002** (Must) — Система повинна ігнорувати роль, передану в запиті реєстрації, і присвоювати новому обліковому запису лише роль «студент». *Джерело:* US-010.
- **FR-003** (Must) — Система повинна відхиляти реєстрацію, якщо адреса електронної пошти вже зареєстрована; адреси порівнюються без урахування регістру. *Джерело:* US-010.
- **FR-004** (Must) — Система повинна зберігати паролі лише як хеші Argon2id і перевіряти пароль повністю, без обрізання. *Джерело:* NFR-3, §8.
- **FR-005** (Must) — Система повинна повертати однакове повідомлення про помилку входу незалежно від того, чи існує обліковий запис із указаною адресою. *Джерело:* US-010.
- **FR-006** (Must) — Система повинна обмежувати кількість послідовних невдалих спроб входу в один обліковий запис. *Джерело:* NFR-3, OQ.
- **FR-007** (Must) — Система повинна розмежовувати доступ до операцій за трьома ролями — студент, провайдер, адміністратор — і відмовляти в операції, на яку роль не має права. *Джерело:* F1, міні-ТЗ §2.3.

### F2. Керування доступністю (FR-010…FR-019)

- **FR-010** (Must) — Система повинна дозволяти провайдеру створювати разові слоти для свого ресурсу із зазначенням дати, часу початку й тривалості в межах A-005. *Джерело:* F2, US-007.
- **FR-011** (Must) — Система повинна відхиляти створення слота, що перетинається в часі з наявним слотом того самого ресурсу. *Джерело:* US-007.
- **FR-012** (Must) — Система повинна дозволяти провайдеру задавати щотижневий шаблон доступності, з якого слоти створюються на горизонт A-001. *Джерело:* F2, US-008.
- **FR-013** (Must) — Система повинна дозволяти провайдеру блокувати проміжок часу на своєму ресурсі. *Джерело:* F2, US-009.
- **FR-014** (Must) — Система повинна скасовувати бронювання, що потрапляють у заблокований проміжок, із причиною, яку вказав провайдер, і залишати цей час недоступним для запису. *Джерело:* US-009, §8.
- **FR-015** (Should) — Система повинна дозволяти провайдеру переглядати календар і завантаження власних ресурсів. *Джерело:* міні-ТЗ §2.3.

### F3. Пошук вільних слотів (FR-020…FR-029)

- **FR-020** (Must) — Система повинна показувати студентові вільні слоти в межах горизонту A-001. *Джерело:* F3, US-004.
- **FR-021** (Must) — Система повинна підтримувати фільтри пошуку за провайдером, типом ресурсу й датою. *Джерело:* F3, US-004.
- **FR-022** (Should) — Система повинна підтримувати фільтр за мінімальною місткістю, застосовуючи його лише до ресурсів типу «аудиторія». *Джерело:* §8.
- **FR-023** (Must) — Система повинна виключати з результатів пошуку слоти, які заброньовані, заблоковані або вже почалися. *Джерело:* US-001, US-004.

### F4. Бронювання (FR-030…FR-039)

- **FR-030** (Must) — Система повинна дозволяти студентові забронювати вільний слот у межах горизонту A-001. *Джерело:* F4, US-001.
- **FR-031** (Must) — Система повинна робити бронювання активним одразу, без підтвердження провайдером. *Джерело:* §8.
- **FR-032** (Must) — Система повинна гарантувати, що на один слот припадає не більше одного активного бронювання, навіть за одночасних запитів. *Джерело:* US-001, NFR-2.
- **FR-033** (Must) — Система повинна відхиляти бронювання, якщо студент уже має максимальну кількість активних бронювань A-002, і називати поточний ліміт. *Джерело:* US-001.
- **FR-034** (Must) — Система повинна закривати запис на слот із моменту його початку A-006. *Джерело:* US-001.
- **FR-035** (Must) — Система повинна відхиляти бронювання слота, що перетинається в часі з наявним активним бронюванням того самого студента. *Джерело:* §8.
- **FR-036** (Must) — Система повинна показувати студентові його активні й минулі бронювання. *Джерело:* F4, US-014.

### F5. Скасування та перенесення (FR-040…FR-049)

- **FR-040** (Must) — Система повинна дозволяти студентові скасувати власне бронювання, якщо до початку слота лишилося не менше ніж A-003. *Джерело:* F5, US-002.
- **FR-041** (Must) — Система повинна визначати граничний час скасування в момент створення бронювання й показувати його в підтвердженні. *Джерело:* §8.
- **FR-042** (Must) — Система повинна звільняти слот одразу після скасування бронювання студентом. *Джерело:* US-002.
- **FR-043** (Must) — Система повинна дозволяти студентові перенести бронювання на інший вільний слот як атомарну заміну: якщо новий слот зайняти не вдалося, старе бронювання лишається чинним. *Джерело:* F5, US-003.
- **FR-044** (Must) — Система повинна застосовувати до перенесення те саме вікно A-003, що й до скасування, і не враховувати перенесення як нове бронювання при перевірці A-002. *Джерело:* US-003.
- **FR-045** (Must) — Система повинна відхиляти скасування й перенесення після початку слота для всіх ролей. *Джерело:* US-002, US-003.

### F6. Сповіщення (FR-050…FR-059)

- **FR-050** (Must) — Система повинна надсилати студентові підтвердження одразу після створення бронювання. *Джерело:* F6, US-001.
- **FR-051** (Must) — Система повинна надсилати студентові нагадування за A-004 до початку слота. *Джерело:* F6, US-005.
- **FR-052** (Must) — Система повинна надсилати провайдеру сповіщення про створення й скасування бронювання на його ресурсі. *Джерело:* F6, US-006.

## 6. Припущення та обмеження

Числа нижче ухвалено командою на сесії узгодження обсягу. З реальними
користувачами їх не перевіряли, тому кожне значення може змінитися —
зміна вноситься через PR, а не правкою на місці.

**Припущення**

- **A-001** — Горизонт бронювання становить 14 днів від поточного моменту. *Джерело:* міні-ТЗ §2.4 (F3), NFR-1.
- **A-002** — Студент може мати не більше 3 активних бронювань одночасно. Значення змінює адміністратор.
- **A-003** — Вікно скасування становить 2 години до початку слота. Значення змінює адміністратор, воно єдине для всієї системи.
- **A-004** — Нагадування надсилається за 24 години до початку слота. Якщо бронювання створено пізніше, ніж за 24 години, надсилається лише підтвердження.
- **A-005** — Тривалість слота — від 15 до 120 хвилин із кроком 5 хвилин.
- **A-006** — Запис на слот закривається в момент його початку.
- **A-007** — Час показується в часовому поясі `Europe/Kyiv`, зберігається в UTC. Щотижневий шаблон доступності задається в київському часі, тому під час сезонного переходу зсувається відносно UTC.

**Обмеження**

- **C-001** — Технологічний стек зафіксовано в міні-ТЗ §2.6: Python 3.12, FastAPI, PostgreSQL 16, pytest, Ruff, Bandit, GitHub Actions, Docker Compose.
- **C-002** — Реальна доставка e-mail і SMS поза обсягом: адаптер сповіщень має локальну заглушку. Через це неможливо підтвердити, що адреса належить людині, яка реєструється.
- **C-003** — Дані в системі синтетичні; реальні персональні дані студентів і викладачів не зберігаються.
- **C-004** — Команда працює над проєктом паралельно з іншими курсами, орієнтовно 7 годин самостійної роботи на тиждень на людину.
- **C-005** — Розгортання демонструється локально через Docker Compose; публічний хостинг не є зобов'язанням.
