# SQL-конкурентність і безпека — локальне продовження

**Дата:** 01.11.2026. **Гілка:** feature/midterm-admin-availability.
Продовження [попереднього етапу](load-worker-calendar-audit.md) після локального
коміту 6f010d7. Зміни призначені для подальшого командного review; push і новий
GitHub CI не виконувалися. Матеріали Лаб8 не змінювалися.

## Відповідність вимогам і архітектурі

Збережено модульний моноліт, PostgreSQL, доменні правила Booking і транзакційний
outbox із HLD та ADR-002/003. Значення PERF-001 (400 мс) і PERF-002 (600 мс)
не змінено. Власник ресурсу, ліміт студента, перетини, дедлайн скасування,
ідемпотентність і включна межа нагадування залишаються тими самими правилами.

Створення броні використовує чотири адресні SQL-команди в одній явно заданій READ COMMITTED
транзакції, з ключем Idempotency-Key і без нього:

1. Окремий statement бере shared advisory gate. Його не об'єднують із читанням:
   snapshot запиту, що очікував gate, міг би лишитися старішим за зміну
   адміністратора. Exclusive gate перехідного Store, адміністративних дій,
   cancel/reschedule та maintenance збережено.
2. Новий statement після gate використовує MATERIALIZED CTE для порядку
   рядок студента → рядок слота та читає актуальні роль, ресурс, блокування
   й політику. Три регресії синхронізовані через pg_locks: зміна ролі,
   політики або блокування перед звільненням gate обов'язково враховується.
3. Наступний statement після очікування row lock читає чинну бронь, активні інтервали
   студента та, за наявності ключа, результат попереднього запиту. Саме новий
   snapshot дозволяє другому запиту побачити переможця і його ключ, а не
   завершитися помилкою унікальності. Повтор скасованої броні повертає її
   актуальний стан; інший payload із тим самим ключем дає 422.
4. Data-modifying CTE створює бронь, а INSERT … SELECT із RETURNING цього CTE
   створює повідомлення та ключ. Залежність явна, COMMIT спільний; помилка
   запису outbox відкочує всі записи. Для початку менш ніж за 24 години є
   два повідомлення, для завчасної броні — три, включно з reminder.

SQL-вирази мають обмежений кеш форми, окремі типізовані bind-параметри й
параметри виконання. Дані користувачів, результати сесій і ролі не кешуються.
Кешована INSERT … SELECT/UNION ALL замінює багаторазове складання й компіляцію
літерального multi-row VALUES. Команда не надсилає повідомлення назовні.

## Блокування й обробка відмов

Для рядків студента і слота використано FOR NO KEY UPDATE: однойменні записи
все ще серіалізуються, але FK-перевірки FOR KEY SHARE сумісні з цим режимом.
Це дозволяє двом користувачам із ролями student/provider бронювати ресурси
одне одного без циклу через FK адресата повідомлення. Частковий UNIQUE і
EXCLUDE лишаються другою лінією захисту; міграції та гарантії довговічності
БД не послаблено.

Узгоджено виконання з ADR-002 п. 6–7: лише створення броні повторює цілу
транзакцію один раз після SQLSTATE 40P01. Повтор починається після ROLLBACK,
не всередині перерваної транзакції. Друга відмова дає 503, Retry-After: 1.
Автоматичний повтор login або інших операцій не додано. Відомі обмеження
uq_booking_slot_confirmed (23505) й ex_slot_active_overlap (23P01) дають
відповідно SLOT_ALREADY_BOOKED і SLOT_OVERLAP (409). Інші помилки не
маскуються під ці конфлікти.

Пул кожного PostgresStore обмежений 32 з'єднаннями, overflow вимкнений,
очікування вільного з'єднання — до 5 с. Пул лінивий: 32 з'єднання не
створюються під час старту. Pool timeout та відмови драйвера повертають
безпечний 503, Retry-After: 1, включно з cookie-автентифікацією.
Збережено pre-ping, connect_timeout 5 с, lock_timeout 5 с і statement_timeout
15 с. Кількість процесів API потрібно враховувати в бюджеті PostgreSQL:
два процеси можуть зайняти до 64 з'єднань плюс Worker/CLI/міграції й резерв.
Додавати наступні процеси без перегляду max_connections не слід.

## Перевірка безпеки змін

- Cookie-сесія читає активний обліковий запис, строк дії та поточні ролі
  одним SQL SELECT. Кешується тільки вираз, не результат. Цей SELECT і
  пошук працюють у DBAPI AUTOCOMMIT; це не поширюється на записи. Окрема
  регресія перевіряє ROLLBACK зміни після такого читання.
- Усередині write-транзакції повторно перевіряються роль student і активність
  акаунта. Старий CurrentUser після деактивації не дає права створити бронь.
  is_demo встановлює лише серверна гілка явно ввімкненого demoBearer;
  cookie-шлях завжди залишає його False. Історичні неактивні демо-фікстури
  доступні тільки в цьому явно дозволеному навчальному режимі.
  Відмову legacy admin-операції після відкликання ролі під час очікування
  exclusive gate також перевірено: наявна повторна перевірка в сервісі працює.
- CSRF, точний Origin, cookie Secure/HttpOnly/SameSite, Argon2id, відключений
  за замовчуванням demoBearer та restricted runtime-роль збережені.
  Чиста перевірка ролі стала async без блокувальних дій; саме SQL-читання
  виконується в робочому потоці.
- Обробники не повертають текст винятків драйвера. SQL-параметри приховані;
  журнали HTTP не містять тіла, cookie, токенів або query string. UI продовжує
  використовувати текстові DOM-вузли, а не HTML із даних користувача.
- Загальний request middleware переведено на прямий ASGI без додаткової
  request/response task group. Стан локальний для запиту; streaming-частини
  передаються відразу, lifespan проходить без HTTP-обробки. Перевіряються
  паралельні request_id/user_id, заголовки, відсутність query/cookie в журналі
  й один запис 500 без тексту необробленого винятку. duration_ms тепер охоплює
  передачу всієї відповіді, тому його не порівнюють із колишнім часом до
  початку streaming. Основною метрикою лишається повний HTTP-час runner.

Це предметний огляд змінених шляхів і регресійні перевірки проєкту,
а не повний незалежний аудит чи зовнішній пентест. Реальні облікові записи
й зовнішні сервіси не використовувалися для перевірок.

## Відтворення навантаження

```powershell
.\.venv\Scripts\python.exe scripts/load_midterm.py --output ..\local-load-results --search-requests 2000
```

Додатковий --api-workers 2 порівнює два процеси API; типовим лишається один.
Зміна кількості процесів не є автоматичним підтвердженням SLA. Без Docker
початкова умова PERF-001/PORT-001 залишається неперевіреною.

Runner запускає власний тимчасовий PostgreSQL і API на loopback, без demoBearer.
Дані: 5000 слотів, 200 користувачів, випадкові cookie/CSRF лише в пам'яті.
Вимірюється весь HTTP-запит до прочитаного та перевіреного тіла, включно із
серверною чергою; p95 — nearest rank. 2000 GET виконуються хвилями по 50,
POST — по 100. Перед хвилями є 5 GET і 10 POST прогріву. Окремо вимірюються
різні слоти, гонка за один слот і різні слоти з Idempotency-Key.
Runner також перевіряє одну confirmed у спірному слоті та сумарні 211 броней,
633 повідомлення, 100 ключів. Пороги і перевірка тіл не відключаються.
Тимчасові процеси й власний кластер прибираються; робоча БД не змінюється.

## Перевірка поточної версії

Повний pytest: **671 passed**, 178,01 с; покриття api + unislot із гілками —
**98,16%**, поріг 90% збережено. Усі 13 локальних воріт завершилися кодом 0:
pytest, Ruff, форматування, Bandit, вимоги, простежуваність,
strict-архітектура/PlantUML, import-linter, OpenAPI, pip check, pip-audit,
whitespace та detect-secrets. Версії залежностей і API-контракт не змінені.

Окремі журнали gate-snapshot-red.txt і gate-snapshot-green.txt містять три
відтворені помилки експериментального об'єднання gate із читанням і три
успішні регресії після розділення statement. Це локальна проміжна помилка,
виправлена до коміту; її не публікували на GitHub. Тест legacy admin-операції
підтвердив наявний захист і не виявив нового обходу цього шляху.

Журнали, JUnit, coverage.json та checks.json — у локальному каталозі
Midterm_features_2026-11-01/performance-security. Це перевірки поточної
робочої гілки, не GitHub CI, не командне схвалення і не запуск на іншому ПК.

## Фактичне навантаження 01.11.2026

Підсумковий прогін поточного runtime з одним процесом API й пулом 32:

| Сценарій | p95 | Відповіді | Висновок |
|---|---:|---|---|
| Пошук, 2000 GET / паралельність 50 | 398,517 мс | 2000 × 200 | ціль 400 мс виконана в цьому native-прогоні |
| Різні слоти, 100 одночасних POST | 591,673 мс | 100 × 201 | ціль 600 мс виконана в цьому прогоні |
| Один слот, 100 одночасних POST | 499,880 мс | 1 × 201, 99 × 409 | одна confirmed у БД |
| Різні слоти з Idempotency-Key, 100 POST | 654,096 мс | 100 × 201 | додаткова перевірка, ціль 600 мс не виконана |

Некоректних тіл — 0; у БД 211 броней, 633 outbox-повідомлення, 100 ключів.
Runner завершився кодом 1 через додатковий сценарій із ключем. Базові часові
цілі досягнуті в цьому native-прогоні з малим запасом; стабільне виконання SLA
і початкову Docker-умову це не підтверджує. Числа попереднього звіту (335,642/826,481 мс)
є окремим історичним виміром, а не підтвердженням цієї версії.

Діагностичні варіанти також збережені, включно з невдалими: інша кількість
потоків/з'єднань, два API-процеси, async Python і окремий Node HTTP-драйвер.
Вони не дали підстав оголосити часові цілі стабільно виконаними. У ранньому
додатковому сценарії 422 спричинив короткий тестовий Idempotency-Key у runner;
ключ виправлено відповідно до контракту, і підсумковий сценарій має 100 × 201.
Невдалий багатопотоковий cProfile-запуск відхилено як вимір: помилки його
інструментації не зараховані до результатів штатного API.

Повні JSON-вибірки та журнали зберігаються поза Git:
Midterm_features_2026-11-01/performance-security/gate-fixed-load і experiments.json.
Скорочений результат і коди 13 воріт збережено також у
[validation/sql-concurrency-2026-11-01.json](validation/sql-concurrency-2026-11-01.json).
Наступний крок продуктивності — профілювання в контрольованому середовищі
з розділеними ресурсами генератора й API; цілі та privacy/RBAC не послаблюються.
Окремо залишаються запуск на ПК іншого учасника, погодження OQ/AQ/DD,
командний review і GitHub CI. Docker-умова не підтверджена; Лаб8 не зачеплено.
