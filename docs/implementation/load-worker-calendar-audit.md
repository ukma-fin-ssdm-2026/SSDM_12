Продовження [Web UI](web-ui.md). База й origin/main після fetch —

## Зміни в робочій системі

- Пошук і читання cookie-сесії виконують адресні SELECT. Фільтри, перевірка
  зайнятості/блокування, курсор і LIMIT застосовуються в PostgreSQL;
  ролі не кешуються. Повний знімок БД на кожну таку операцію не створюється.
- POST бронювання використовує ту саму доменну перевірку, але адресні SQL-команди.
  Порядок lock: shared advisory gate → рядок студента → рядок слота.
  Незалежні бронювання можуть виконуватись паралельно; ліміт одного студента
  й одна бронь на слот захищені. Старі cancel/reschedule/admin/maintenance
  використовують exclusive gate, тому не перезаписують конкурентні зміни.
  Перевірка переможця повторюється новим SQL statement після очікування lock.
  Бронь, ідемпотентність та outbox комітяться разом; збої відкочують усе.
- Однаковий payload сповіщення формується спільною build_notification для SQL
  і memory-адаптерів. Контракт повтору ключа не змінено: інший slot_id дає 422.
- Міграція 0004 адитивно додає індекси пошуку/студента/блокування й технічну
  maintenance_checkpoint. Старі міграції та записи не переписано. Час SQL-сесій
  явно UTC, lock_timeout 5 с, statement_timeout 15 с. UI обмежує очікування
  fetch двадцятьма секундами, зберігаючи ключ неоднозначного POST для повтору.
- Worker розширює горизонт шаблонів на старті й раз на годину; інтервал можна
  задати --horizon-interval. Без Worker пошук має fallback один раз на київську
  дату. Checkpoint змінюється в тій самій транзакції, дублікати не створюються.
  Тимчасовий DBAPI-збій у циклі дає безпечний worker_retry без DSN і нову спробу;
  --once завершується кодом 1. Помилки початкової конфігурації не приховуються.
- manage_notifications.py показує мінімальний список failed і дозволяє явний
  повтор одного ID. Потрібні ID активного admin та причина, дія пишеться в аудит.
  ID доставки зберігається, повтор не дублює скриньку. Скасоване бронювання
  чи нагадування після початку слота не відправляються: стан стає cancelled.
- За прямим запитом Дениса 31.10 у локальний обсяг додано FR-015 і FR-068.
  Календар власного ресурсу показує минулі/майбутні інтервали та підсумки
  занятості, без імен чи ID студентів. Admin читає аудит із датами, автором,
  точною назвою дії та before/after. Змінювати журнал через API не можна.
  Період читання обмежений 31 днем, списки мають limit/offset. Відкритий OQ-004
  має відобразити це рішення після командного огляду PR; його статус не підроблено.

Нові операції: GET /api/v1/resources/{resource_id}/calendar та
GET /api/v1/admin/audit. Загалом **32 операції API**; OpenAPI згенеровано з коду.

## Вимір навантаження

Runner scripts/load_midterm.py створює лише власний тимчасовий PostgreSQL-кластер,
мігрує порожню БД, наповнює рівно 200 синтетичних користувачів і 5000 слотів.
API працює окремим процесом, demoBearer=0; авторизація — справжні cookie-сесії
з хешами в БД. Сесії готує фікстура; час Argon2/login не входить у ці метрики.
База, API та генератор навантаження розташовані на цьому самому Windows ПК.
Це локальний native-заміp, а не перевірка публічного Render-сервісу.

Методика: nearest-rank p95, п'ять прогрівальних GET, десять послідовних
прогрівальних бронювань, потім повні хвилі 50 або 100 HTTP-запитів.
Враховано читання тіла, серверну чергу та очікування з'єднання. Перевіряються
не лише статуси: пошук повертає 20 слотів; 201 містить запитаний slot_id;
відмови гонки мають SLOT_ALREADY_BOOKED. Після гонки перевіряється БД.
Пороги не послаблювались, fsync/synchronous_commit не вимикались.

| Сценарій | Обсяг | p95 | Результат |
|---|---|---|---|
| Пошук | 2000 запитів, паралельність 50 | 335,642 мс | 2000 × 200; ціль ≤400 мс виконана на native Windows |
| Різні слоти | 100 одночасних POST | 826,481 мс | 100 × 201, але ціль ≤600 мс **не виконана** |
| Один слот | 100 одночасних POST | 531,745 мс | 1 × 201, 99 × 409; у БД рівно 1 confirmed |

Помилкових тіл — 0. Перед оптимізацією короткий прогін на 100 GET мав p95
55576,653 мс, 100 різних POST — 112921,380 мс; це діагностичний baseline,
не та сама кількість запитів/прогріву, що фінальний сценарій. Збережено всі
невдалі проміжні результати. Код завершення фінального load-run — 1 саме через
ціль 600 мс; функціональна успішність 100 POST не видається за успіх SLA.

```powershell
.\.venv\Scripts\python.exe scripts/load_midterm.py --output ..\local-load-results
```

Не запускати одночасно з іншими важкими замірами. Параметр --search-requests
допускає діагностичні короткі хвилі, стандартно 2000. Дані робочої БД й системний
PostgreSQL не використовуються. Runner зупиняє власне дерево API-процесів
і видаляє лише перевірений pgdata/load-*.

## Запуск та операторські команди

Після оновлення джерел на кожному комп'ютері:

```powershell
.\.venv\Scripts\python.exe scripts/manage_db.py local-init
.\.venv\Scripts\python.exe scripts/manage_db.py migrate --env-file .env.migrations.local
.\.venv\Scripts\python.exe -m uvicorn api.main:app --app-dir src --env-file .env.local --port 3000
```

Worker у другому терміналі:

```powershell
.\.venv\Scripts\python.exe scripts/run_worker.py --env-file .env.local
.\.venv\Scripts\python.exe scripts/manage_notifications.py --env-file .env.local failed --limit 50
```

Для повтору конкретного failed ID викликати manage_notifications.py --env-file
.env.local retry з UUID повідомлення, --actor-id UUID активного адміністратора
та --reason з фактичною причиною. Значення брати зі свого списку й акаунта,
не копіювати навчальні UUID. CLI використовує restricted runtime URL;
власника БД не використовує. Оператор із доступом до цього URL уже має
відповідні SQL-права: це локальний інструмент, не публічний endpoint.

## Перевірки та наступні кроки

Повний локальний pytest: **649 passed**, 108,36 с; api + unislot з гілками —
**98,21%**, поріг 90% збережено. SQL і memory порівняно за фільтрами та
курсором, перевірено UTC, усі відмови бронювання, повтор скасованої броні,
паралельний ліміт одного студента, rollback outbox/аудиту, CLI та Worker
окремим процесом. Додані календар/аудит охоплені таблицею ролей і privacy sweep.
Усі 13 локальних воріт у checks.json завершились кодом 0: pytest, Ruff,
формат, Bandit, вимоги, простежуваність, strict-архітектура/PlantUML,
import-linter, OpenAPI, pip check, pip-audit, whitespace та detect-secrets.
Незалежне командне рев'ю або новий GitHub CI не заявляються.

Браузерний огляд на окремій БД: створена студентом бронь з'явилась у календарі
провайдера (3 слоти, 1 зайнятий, 2 вільні); адмін відфільтрував resource.create,
прочитав автора й before/after, перевірив порожній результат. На 390×844
аудит не мав горизонтального переповнення; попередження/помилки console — 0.
Скріншоти, JSON/JUnit/coverage й логи — Midterm_features_2026-10-31/load-worker
поза репозиторієм. Окремо створено чисту копію runtime-джерел, новий venv,
установлено зафіксовані requirements-dev.txt, мігровано нову ізольовану БД.
На цій копії пройшли UI/MIME, register/login/search/logout із cookie, окремий
Worker, notification CLI та pip check. Це та сама Windows-машина, а не інший
комп'ютер; результат — clean-launch.json, журнал — clean-install.txt.
Наявну робочу локальну БД pgdata/dev оновлено до 0004 без скидання даних,
її попередній стан запуску збережено. Тимчасові API/Worker/кластери огляду зупинені.

у локальному файлі PR-preparation.md поряд з артефактами. Коміти створено
