# PostgreSQL, атомарний outbox та незмінний аудит

**Дата:** 31.10.2026. **Гілка:** `feature/midterm-admin-availability`.
База: main `7e384d251c3c267d340a6f2e9aece704241a56a7`, після локальних етапів
[адміністрування](midterm-admin-availability.md) і [шаблонів](weekly-templates.md).
Зміни локальні: нового PR, push, GitHub CI чи злиття тут не заявлено.

## Поведінка й вимоги

- PostgreSQL зберігає користувачів і ролі, ресурси, шаблони, слоти, блокування,
  версії політики, бронювання, ключі ідемпотентності, аудит та чергу повідомлень.
  Старт API не скидає дані й не виконує міграції. Наповнення demo — окрема команда,
  що зберігає наявні дані, якщо користувачі вже існують.
- FR-050/052: бронювання записує підтвердження студенту та повідомлення провайдеру.
  Скасування студентом повідомляє провайдера; блокування провайдером повідомляє
  студентів із причиною. Payload містить ресурс, час і дедлайн скасування.
  Повтор Idempotency-Key не створює дубль повідомлень.
- FR-051/054: reminder має `scheduled_for = starts_at − 24 год`; включна межа
  PR #232 збережена. Worker не бере майбутнє повідомлення до настання цього часу.
  Успішне перенесення скасовує старе нагадування й планує нове; невдале зберігає
  стару бронь та чергу. Скасування захопленого нагадування скидає lease.
- FR-053/REL-002: бронювання та outbox комітяться разом. Відмова запису outbox
  відкочує бронь і ключ ідемпотентності. Адаптер доставки не викликається з HTTP;
  його недоступність не заважає створити бронь.
- Worker бере записи через `FOR UPDATE SKIP LOCKED`, комітить lease, потім викликає
  адаптер поза транзакцією бронювання. Після помилки зберігається повтор із затримкою;
  аварія процесу відновлюється через lease. Прострочений claim_token не може
  підтвердити нову спробу. Після вичерпання спроб запис лишається як `failed`.
- Параметри Worker: 8 спроб, 5 с початкова затримка, межа 3600 с, lease 30 с за
  замовчуванням. Це конфігурація локального етапу для огляду, не нові погоджені NFR.
- FR-066/067: адміністративна зміна й аудит атомарні. Runtime-роль має лише
  INSERT/SELECT на аудит; UPDATE/DELETE/TRUNCATE заборонені. Тригери додатково
  блокують мутації звичайним SQL навіть власником, доки захист не вимкнено власником.
  API відхиляє owner/superuser URL. Аудит не можна перезаписати й через Store.

## Доставка за C-002

Справжнього e-mail/SMS немає: C-002 передбачає локальну заглушку.
`MailboxGateway` записує повідомлення у постійну особисту скриньку.
GET `/api/v1/me/notifications` із limit/offset показує лише доставлені повідомлення
поточного адресата; загалом 23 операції API. Унікальний ID запобігає дублю в скриньці
після аварії між доставкою та ack. Майбутній зовнішній провайдер має підтримувати
той самий ключ ідемпотентності; exactly-once для довільного SMTP не заявляється.

Скасування до запису скриньки запобігає старому reminder; уже доставлене повідомлення
відкликати неможливо. Worker опитує чергу раз на 1 с за замовчуванням;
точний real-time SLA не вимірювався.

## Реалізація та обмеження

SQLAlchemy Core + psycopg 3; Alembic 0001 містить заморожений SQL, 0002 додає
`next_attempt_at`. Стара міграція не створює схему зі змінюваної поточної metadata.
Встановлено btree_gist; active-slot EXCLUDE, unique confirmed booking, FK та CHECK
працюють у PostgreSQL. `slot.is_active=false` зберігає історію, дозволяючи новому
шаблону створити активний слот поверх архівного інтервалу.

Перехідний PostgresStore завантажує реляційні записи в існуючі dataclass-сервіси та
зберігає дельту. Один транзакційний advisory lock серіалізує API між процесами.
Це межа коректності, а не завершений масштабований repository layer: потрібні
адресні SQL-запити та виміри PERF-001/002. Вкладені lock використовують транзакцію
маршруту; перехоплений внутрішній виняток усе одно позначає її rollback-only.

SQL-помилки, включно з читанням ролі під час автентифікації, повертають 503
TRANSIENT_CONFLICT із Retry-After без DSN, SQL і паролів. Повтор POST бронювання
виконуйте з тим самим Idempotency-Key. Автоповтор усього HTTP-запиту не заявляється.

## Локальний запуск

Команди з кореня репозиторію; Python 3.12+, PostgreSQL 16 із initdb/pg_ctl.
За потреби задайте UNISLOT_POSTGRES_BIN до каталогу bin PostgreSQL.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe scripts/manage_db.py local-init
.\.venv\Scripts\python.exe scripts/manage_db.py migrate --env-file .env.migrations.local
.\.venv\Scripts\python.exe -m uvicorn api.main:app --app-dir src --env-file .env.local --port 3000
```

local-init створює окремий кластер pgdata/dev на 127.0.0.1:55436, базу unislot_local.
Наявний системний PostgreSQL не змінюється. Повторний виклик піднімає той самий
кластер; після оновлення коду запускайте migrate окремо. Випадкові паролі лишаються
в ігнорованих файлах: `.env.local` — runtime-роль API/Worker, `.env.migrations.local`
— owner CLI міграцій. Ці файли не включаються в PR, командні архіви чи відео.

Другий термінал у цьому репозиторії:

```powershell
.\.venv\Scripts\python.exe scripts/run_worker.py --env-file .env.local
```

Swagger: http://127.0.0.1:3000/api-docs. Локальний env явно дозволяє демо-токени.
З demo-student створіть бронь із унікальним Idempotency-Key, прочитайте
/me/notifications. Провайдер бачить своє повідомлення після авторизації його токеном.
`--once` запускає Worker один раз. Ін'єкція збою лише в терміналі Worker:

```powershell
$env:UNISLOT_NOTIFICATION_FAILURE = '1'
.\.venv\Scripts\python.exe scripts/run_worker.py --env-file .env.local --once
Remove-Item Env:UNISLOT_NOTIFICATION_FAILURE
.\.venv\Scripts\python.exe scripts/run_worker.py --env-file .env.local --once
```

Повтор береться після next_attempt_at; негайний другий прогін не обходить затримку.
Після завершення зупиніть API/Worker через Ctrl+C, потім:

```powershell
.\.venv\Scripts\python.exe scripts/manage_db.py stop-local
```

Для зовнішньої БД власник запускає migrate з UNISLOT_ADMIN_DATABASE_URL та
UNISLOT_APP_ROLE (роль уже має існувати). API/Worker отримують лише
UNISLOT_DATABASE_URL. Destructive downgrade заборонено; відновлення — з backup.

## Перевірки

tests/integration створює окремий тимчасовий кластер pgdata/tests-*, унікальні БД
та ролі. Після тестів зупиняє й видаляє лише власні дані. Потрібні PostgreSQL
binaries, пароль системної БД не потрібен. Тести не пропускаються автоматично за
відсутності БД. Linux/macOS запускають ті самі Python-команди зі свого venv;
initdb повинен працювати звичайним користувачем, не root.

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/integration tests/unit/test_retry_policy.py
.\.venv\Scripts\python.exe -m pytest -q --cov=api --cov=unislot --cov-branch --cov-fail-under=90
.\.venv\Scripts\ruff.exe check src tests scripts migrations
.\.venv\Scripts\ruff.exe format --check src tests scripts migrations
.\.venv\Scripts\bandit.exe -q -r src scripts
.\.venv\Scripts\pip-audit.exe -r requirements-dev.txt --progress-spinner off
```

**Фактичний фінальний прогін:** Windows 10, Python 3.13.13, PostgreSQL 16:
**530 passed за 58,24 с**, сукупне покриття рядків і гілок api + unislot — **98,42%**
при незміненому порозі 90%. Тести підтвердили:

- читання броні окремим процесом API й доставку окремим процесом Worker;
- одну переможну транзакцію з 12 незалежних спроб зайняти той самий слот;
- відкат броні/ідемпотентності при збої outbox, відкат адміністративної правки при
  збої аудиту, відновлення lock після невдалого підключення;
- SQL-відмови runtime-ролі й тригерів аудиту, active-slot EXCLUDE та unique booking;
- приватність скриньок, перенесення, блокування з причиною, повтори без дубля після
  аварії, відхилення старого lease та збереження failed;
- локальне створення броні за ≤ 2 с при контрольованій недоступності адаптера.
  Це вимір цього сценарію, не навантажувальний SLA для всіх конфігурацій.

Усі 13 перевірок у checks.json завершилися кодом 0: pytest, Ruff, форматування,
Bandit, вимоги, простежуваність, архітектура зі strict і синтаксисом PlantUML,
обидва import-linter контракти, OpenAPI, pip check, pip-audit, whitespace та
сканер секретів для tracked і нових неігнорованих файлів. Аудит установленого
середовища не знайшов відомих вразливостей; pip у локальному venv оновлено до
26.2.2 відповідно до наявної команди CI. Попередження pip-audit про недоступний
кеш не перешкодило завершеному аудиту.

Окремі локальні JSON/JUnit/log артефакти лежать поза репозиторієм у
Midterm_features_2026-10-31/postgres-outbox; історичні звіти Лаб6 не перезаписуються.

## Наступні кроки

Наступним локальним етапом [Auth](password-auth.md) реалізовано реєстрацію та
парольні сесії. Перелік нижче фіксує межу саме попереднього етапу PostgreSQL.

Справжня реєстрація й парольні сесії FR-001…006, поріг входу після OQ-001,
користувацький UI, Docker Compose, навантажувальні виміри й експлуатація Worker.
Демо-токени залишаються заглушкою, за замовчуванням вимкнені. Для failed ще потрібна
операційна команда ручного повтору; дані збережені для аналізу. PostgreSQL superuser
може вимкнути захист аудиту, тому FR-067 доведено для runtime-ролі та звичайного SQL
з увімкненими тригерами, а не проти зловмисного власника інфраструктури.

Матеріали Лаб8, версію API, теги та реліз не змінено. Відсоток оцінювання #240
за цими тестами автоматично не перераховується.
