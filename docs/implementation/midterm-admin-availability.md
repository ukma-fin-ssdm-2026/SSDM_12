## API

Шляхи відповідають HLD §5.1, префікс — `/api/v1`.

| Метод і шлях | Право | Успішна відповідь |
|---|---|---|
| PUT `/admin/users/{user_id}/roles/{role}` | admin | 200, поточні ролі |
| DELETE `/admin/users/{user_id}/roles/{role}` | admin | 200, поточні ролі |
| GET `/admin/policies/current` | admin | 200, версія політики |
| PUT `/admin/policies/current` | admin | 200, чинна версія |
| POST `/resources/{resource_id}/blocks` | провайдер цього ресурсу | 201, блокування й кількість скасувань без ID студентів |
| DELETE `/resources/{resource_id}/blocks/{block_id}` | провайдер цього ресурсу | 204, без тіла |

Тіло PUT політики: `{"booking_limit": 5, "cancel_window_minutes": 180}`.
Тіло POST блокування: `starts_at`, `ends_at` із часовим поясом та непорожня `reason`.
Специфікацію й каталог помилок перегенеровано з коду; тепер у застосунку 20 операцій.

## Межі висновку й припущення для огляду

- Сховище лишається в пам'яті. Перезапуск скидає ролі, політики, блокування й аудит.
  Права справді перевіряються, але особу досі визначає демо-токен; реєстрації, паролів і сесій немає.
- `store.lock` захищає один процес, а не кілька процесів чи PostgreSQL-транзакції.
- FR-067 не виконано: Python-список аудиту не дає незмінності на рівні БД.
- Сповіщення про скасування ще не надсилаються: FR-050/052/053 і весь US-009 не позначаємо завершеними.
- AQ-02: реалізовано запропоновану в HLD відмову від зняття ролі provider до перепризначення ресурсів,
  щоб зберегти INV-15. Це вибір реалізації для огляду; командне ухвалення AQ-02 не заявляється.
- Кілька ролей підтримує наявна модель; рішення AQ-01 не позначаємо ухваленим від імені команди.
- Зниження ліміту не скасовує чинні бронювання; воно впливає на наступні спроби створення.
- Вікно політики задається цілим числом хвилин; надто велике значення, що спричинило б
  вихід дедлайну за межі datetime, дає 422 до будь-яких змін.
- Зняття блокування не відновлює скасованих бронювань. Інші блокування того самого часу діють далі.

Ці перевірки підтверджують поведінку прототипу; відсоток готовності за рубрикою викладача
і зарахування вимог як повністю виконаних не обчислювалися.

## Наступні етапи й інтеграція

1. Перед публікацією оформити окреме issue цієї зміни з посиланням на #240;
   додати його до опису PR за CONTRIBUTING. Огляд: власники `src/`, `tests/` та RTM у CODEOWNERS.
2. Окремою зміною під'єднати постійне сховище, міграції та транзакції; перенести ці сценарії
   зі `stubs` до application/infrastructure без зміни описаних шляхів API.
3. FR-012 реалізовано наступним локальним етапом, див. [звіт](weekly-templates.md).
   Далі — outbox/Worker/адаптер FR-050/052/053 за ADR-003 після появи транзакційного
   сховища. FR-067 спирається на права БД і тригер DD-08.
4. Кожну наступну функцію починати від актуального main; зміни в `routers.ALL`, сховищі,
   RTM та згенерованій OpenAPI узгоджувати в тому самому PR. Після злиття перегенерувати
   OpenAPI з об'єднаного коду й виконати повний набір тестів.

Матеріали Лаб8 (`docs/refactoring/`, `.sonarcloud.properties`), конфігурація версії,
CHANGELOG і теги в цьому етапі не змінювалися.
