Наступний етап після [ролей, політики й блокування](midterm-admin-availability.md),
на тій самій базі main `7e384d251c3c267d340a6f2e9aece704241a56a7`.

## Поведінка FR-012 і критерії US-008

- Провайдер задає ISO-день тижня (1–7), локальні початок і кінець за Europe/Kyiv,
  тривалість слота за A-005 та дати дії `valid_from`/`valid_to` включно.
- Під час збереження створюються майбутні слоти на горизонт A-001. Повторний
  чи паралельний PUT не створює дублікати.
- Сезонний перехід змінює UTC-момент, зберігаючи локальну годину. Неіснуючий,
  неоднозначний час або зміна абсолютної тривалості в момент переходу повертаються
  як конфлікти; API не обирає fold і не пересуває початок мовчки.
- Кандидати, що перетинають разові чи інші активні слоти, не створюються;
  `conflicts` перелічує всі слоти, які заважають. Неконфліктні кандидати створюються.
- Зміна шаблону оновлює майбутні незаброньовані слоти, зберігаючи активні бронювання,
  їхні ID слотів, дедлайни, політики й заплановані нагадування.
- Історичний скасований запис бронювання зберігає посилання на свій слот. Якщо слот
  відкликано новим розкладом, його не видно у вільному пошуку й не можна забронювати
  за старим UUID: 409 SLOT_WITHDRAWN.
- Якщо збережене через активну бронь старе місце потім звільнили скасуванням, перевірка
  перед наступним бронюванням відкликає його, якщо воно вже поза чинним розкладом.
- Горизонт продовжується перед пошуком, перевіркою слота, створенням/перенесенням броні
  та читанням шаблону. Ці виклики матеріалізують похідні дані; повтор ідемпотентний.

## API

Власний ресурс провайдера, префікс `/api/v1`:

- PUT `/resources/{resource_id}/templates/{template_id}` — 201 для нового UUIDv4,
  200 для оновлення. Шлях PUT відповідає HLD §5.1.
- GET `/resources/{resource_id}/templates/{template_id}` — поточне правило й звіт
  генерації; додано для перевірки конфліктів провайдером.

Приклад тіла:

```json
{
  "weekday": 3,
  "start_local": "14:00",
  "end_local": "16:00",
  "slot_minutes": 30,
  "valid_from": "2026-10-19",
  "valid_to": null
}
```

Із відповіді видно `created_slots`, `withdrawn_slots`, `retained_booked_slots` та
`conflicts`. Кожен конфлікт містить дату, локальний час, код і, для перетину,
ID слота власного ресурсу; даних студентів немає.
Неправильна форма розкладу дає 422 до зміни стану. Чужий ресурс — 403;
відсутній шаблон власного ресурсу — 404. Не можна переприв'язати чужий UUID шаблону
до свого ресурсу.

## Межі й підготовка до постійного сховища

- Шаблони й слоти ще в пам'яті. Перезапуск скидає зміни. Окремого довготривалого
  процесу Worker немає; зараз використано актуалізацію на запит. `extend_horizon(now)`
  доступний для подальшого виклику з Worker після під'єднання сховища.
- Один шаблон описує проміжок одного локального дня з точністю до хвилини, що
  ділиться на цілі слоти. Нічний розклад задається окремими шаблонами по днях.
- Вибір не створювати неоднозначні DST-кандидати — явна поведінка цієї локальної
  реалізації для огляду; командне ухвалення нового правила не заявляється.
- `slot.is_active` зберігає історію без повторного продажу відкликаного часу. Перед
  перенесенням до PostgreSQL потрібна міграція для цього стану й EXCLUDE лише
  активних слотів або еквівалентна архівна модель: старе EXCLUDE для всіх рядків
  заборонило б новий слот поверх скасованої історії. Це відмінність адаптера від
  початкової ER-моделі, записана також у data-model.md §9.
- Навантажувальні цілі PERF-001/002 на PostgreSQL цим прогоном не перевірялися.
- Оцінку готовності продукту за рубрикою викладача не перераховано.

Наступний етап: постійне сховище й транзакційна межа для бронювання/outbox.
Після цього FR-050/052/053 реалізуються за ADR-003; FR-067 — за DD-08.
Створення незалежної черги лише в пам'яті суперечило б прийнятому ADR-003.
Матеріали й завдання Лаб8 цим етапом не змінено.
