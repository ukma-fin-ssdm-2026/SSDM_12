# Завершення локальної перевірки продуктивності — 01.11.2026

Продовження [SQL-конкурентності](sql-concurrency-hardening.md). Мета — p95
пошуку ≤400 мс, створення броні ≤600 мс, включно з Idempotency-Key.
Пороги, кількість користувачів/слотів, паралельність і перевірки тіл не змінені.
Попередній звіт із 654,096 мс для ключа збережений як історичний результат.

## Зміни й транзакційна межа

Адитивна міграція 0005 додає public.booking_context без змін таблиць і даних.
Це інфраструктурний read/lock helper: gate → рядок студента → рядок слота →
поточний стан і попередній результат ключа. Усі ці дії виконуються одним
клієнтським SQL-викликом. Перевірки горизонту, ліміту, перетинів, дедлайну й
нагадувань залишаються чистими правилами Python. Другий клієнтський SQL-запит
атомарно записує бронь, outbox і ключ, як на попередньому етапі. Один COMMIT
і той самий READ COMMITTED охоплюють обидва виклики; зовнішньої доставки тут немає.

Функція явно VOLATILE: окремі SQL-команди всередині PL/pgSQL отримують свіжі
snapshot після очікування gate і row lock. Це принципово відрізняється від
об'єднання всього в один CTE. Регресії зміни ролі, політики та блокування,
конкурентного ключа й ліміту студента збережені. FOR NO KEY UPDATE, частковий
UNIQUE, EXCLUDE та обмежений retry після deadlock не послаблені.

Функція SECURITY INVOKER, із фіксованим search_path і кваліфікованими таблицями.
PUBLIC не має EXECUTE; runtime отримує явний grant і не отримує прав власника.
Старт відхиляє відсутню функцію, STABLE, SECURITY DEFINER або відсутній grant.
Окремий тест оновлює схему з 0004 до 0005 двічі, порівнює старі броні й
створює нову після оновлення. Демо-маркер встановлюється сервером лише в
явно дозволеному режимі; реальна cookie-автентифікація та CSRF не змінені.

Пошук кешує до 32 форм параметризованого SQL, не результати чи значення
фільтрів. Перевірено зміну провайдера, типу, дати, місткості, limit і поточних
рядків при тій самій формі. Відповідь проходить один рекурсивний
SlotList.model_validate замість окремих Python-конструкторів кожної вкладеної
моделі; повна перевірка типів і контракт залишаються чинними.

## Профіль запуску

Виміряний профіль: два процеси Uvicorn, до 32 з'єднань у пулі кожного,
звичайний pool_pre_ping на кожному checkout, без overflow. На Windows lifespan
встановлює інтервал перемикання потоків CPython 1 мс; після shutdown або
помилки startup попереднє значення відновлюється. Значення
UNISLOT_THREAD_SWITCH_INTERVAL_MS дозволене в межах 1–20 мс, типове — 1.
На інших ОС інтервал інтерпретатора не змінюється. Це налаштування процесу,
а не глобальної конфігурації Windows. Воно перевірене окремими тестами.

Два API-процеси можуть зайняти до 64 з'єднань. Для Worker/CLI/міграцій і
резерву PostgreSQL потрібен окремий бюджет. Без зміни пулу додавати наступні
процеси не слід. Значення fsync/synchronous_commit, query/lock timeout,
перевірки ролей, сесій, Origin і CSRF збережені.

Це локальне вимірювання, а не оцінка Render-хостингу. Поточна PERF-001 вимагає
нативне середовище; архівні JSON/звіти зберігають умови, що діяли на час тих вимірювань.

Для вже підготовленої локальної БД, з кореня репозиторію:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/manage_db.py migrate --env-file .env.migrations.local
$env:UNISLOT_DEMO_AUTH = '0'
$env:UNISLOT_THREAD_SWITCH_INTERVAL_MS = '1'
.\.venv\Scripts\python.exe -m uvicorn api.main:app --app-dir src --env-file .env.local --workers 2 --port 3000
```

Worker запускається окремо за [інструкцією](load-worker-calendar-audit.md#запуск-та-операторські-команди).
Початкове створення БД й адміністратора — у [Web UI](web-ui.md).
Режим --reload призначений для розробки з одним процесом; цей вимір виконано
без нього. Для іншої конфігурації наведені нижче числа автоматично не переносяться.

## Три завершальні послідовні прогони

Команда кожного прогону, з окремим output-каталогом:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/load_midterm.py --output ..\local-load-results --search-requests 2000 --api-workers 2
```

У кожному новому ізольованому PostgreSQL: 5000 слотів, 200 користувачів,
реальні cookie/CSRF, demoBearer вимкнений. Пошук — 2000 GET із паралельністю 50;
три хвилі POST — по 100. Прогрів незмінний: 5 GET і 10 POST. Вимір від початку
HTTP-запиту до перевіреного тіла; percentile — nearest rank. Профілер у цих
трьох прогонах не працював.

| Різні слоти без ключа | 405,386 | 487,696 | 434,388 | ≤600 |
| Різні слоти з ключем | 367,581 | 388,557 | 403,618 | ≤600 |

Після кожного прогону: одна confirmed у спірному слоті, 211 броней,
633 outbox-повідомлення й 100 ключів. Тимчасові кластери й процеси прибрані.
Скорочені результати з конфігурацією та кодами завершення — у

Це підтверджує виконання локального пункту плану для зазначеного профілю.
PERF-001 відповідає поточному нативному профілю, але ці цифри не є заміром Render.
PORT-001 потребує окремого повторення процедури з чистого клону й фіксації часу.
Пороги вимог і статуси командних ADR/OQ не змінені; матеріали Лаб8 не редагувалися.
Новий GitHub CI не заявляється.

## Профілювання та докази

Діагностичні прогони, включно з невдалими одно-процесними варіантами,
збережені поза Git у Midterm_features_2026-11-01/performance-completion.
Фінальні сирі вибірки — final-01, final-02, final-03/results.json.
py-spy 0.4.2 установлено лише в окремий diagnostic-tools, без змін залежностей
проєкту. Профіль власного тестового API містить тільки стеки, без locals,
аргументів і токенів: 1198 семплів, помилок 0. Профіль не зараховувався як
кваліфікаційний замір; джерелом результатів є три штатні запуски вище.
Окрема похідна QA-12 описує межі й відновлення налаштування потоків;
її unit-тести не підміняють навантажувальний доказ PERF-001/002.

## Підсумкові перевірки й локальна БД

Повний pytest — **684 passed**, 162,97 с; покриття api + unislot із гілками —
**98,29%**, поріг 90% збережено. Усі 13 локальних воріт завершилися кодом 0:
pytest, Ruff, формат, Bandit, вимоги, простежуваність, strict-архітектура/PlantUML,
import-linter, OpenAPI, pip check, pip-audit, whitespace, detect-secrets.
Окремо перевірено 1 і 20 мс, відхилення 0/21 мс, відновлення після startup failure,
властивості/права helper, повтор міграції без втрати старих броней та свіжі фільтри.

Власну pgdata/dev оновлено з 0004 до 0005. Кількості користувачів, ресурсів,
слотів, броней, outbox і аудиту не змінилися; restricted runtime startup check
пройшов. БД була зупинена до оновлення й повернута в цей стан після нього;
системний PostgreSQL не змінювався. Доказ — local-db-upgrade.json поза Git.
Push, новий PR, командний review і GitHub CI не виконувалися.
