Специфікація відповідає на питання «що саме приймає й повертає кожна кінцева точка».
Цей документ — на питання «чому вона така»: які ресурси ми виділили, які коди стану
обрали, як влаштовані помилки, пагінація, версіонування й безпека.

Каталог у §3 описує цільовий стан після злиття модулів бронювань, слотів і ресурсів.
До того часу кількість операцій у `main` може бути меншою за 14; усі 14 звірено зі
згенерованою специфікацією повного командного пакета Лаб 4.

## 1. Огляд архітектури

| Аспект | Рішення |
|---|---|
| Базова адреса | `http://localhost:3000/api/v1`; службова `GET /health` — поза версією контракту |
| Стиль API | REST поверх HTTP; компонент `REST API` модульного моноліту (HLD §4, ADR-001) |
| Формат | `application/json`; помилки — `application/problem+json` (RFC 9457, §4.4) |
| Автентифікація | Лаб 4 — демо-токени `Authorization: Bearer demo-<роль>`; цільова — сесія в cookie HttpOnly (DD-06), відхилення пояснено в §5 |
| Авторизація | deny-by-default: кожна операція, крім `/health`, вимагає токен і роль; власника об'єкта перевіряє сервіс (THR-03) |
| Версіонування | MAJOR у шляху (`/api/v1`); повна версія контракту — `info.version` = `1.0.0-alpha.1` і заголовок `API-Version` у кожній відповіді (§4.9) |
| Документація | генерується з коду FastAPI: під час старту сервера, скриптом і в CI; публікується на GitHub Pages |
| Ідентифікатори | UUID (DD-13) |
| Час | RFC 3339 в UTC; фільтр `date` у пошуку — дата за Києвом (A-007) |
| Іменування | шляхи — іменники в множині (`/slots`, `/bookings`); поля й параметри — `snake_case`; дії — дієслово після ресурсу (`/bookings/{id}/cancel`) |

**Як влаштовано код.** `src/api/routers/` — роутери за модулями (тонкий шар HTTP: валідація,
статуси, заголовки); `src/api/schemas/` — схеми Pydantic, з яких FastAPI будує
`components/schemas`; `src/api/stubs/` — заглушки сервісів, названі за інтерфейсами HLD §5.2
(`BookingService`, `SlotSearch`, `ResourceManagement`), і сховище демо-даних у пам'яті;
`src/api/errors.py` — каталог помилок; `src/api/security.py` — автентифікація й ролі. Де
лежить код компонента і як його замінять справжні модулі, фіксує DD-17 у HLD §10.

## 2. Модель ресурсів

### Ресурс `resources`

- **Кінцеві точки:** `GET /resources`, `GET /resources/{resource_id}`,
  `POST /admin/resources`, `PATCH /admin/resources/{resource_id}`
- **Опис:** каталог консультацій і аудиторій; створює й змінює їх лише адміністратор (US-011).
- **Атрибути:**
  - `id` (uuid) — ідентифікатор
  - `name` (string, 1–120) — назва; пробіли на краях обрізаються
  - `type` (enum `consultation` | `room`) — після створення не змінюється
  - `capacity` (integer 1–1000 або `null`) — лише для `room` (INV-08)
  - `provider` (`PersonSummary`: `id`, `full_name`) — провайдер ресурсу
- **Зв'язки:** має рівно одного провайдера — користувача з роллю `provider` (INV-15);
  має багато слотів (`/resources/{resource_id}/slots`).
- **Вимоги:** FR-021, FR-060, FR-061, FR-066.

### Ресурс `slots`

- **Кінцеві точки:** `GET /slots` (пошук вільних), `GET /slots/{slot_id}`,
  `POST /resources/{resource_id}/slots` (разовий слот провайдера)
- **Опис:** проміжок часу на ресурсі, доступний для бронювання.
- **Атрибути:**
  - `id` (uuid)
  - `starts_at`, `ends_at` (date-time, UTC) — півінтервал: кінець слоту не належить
  - `duration_minutes` (integer) — 15–120 із кроком 5 (A-005)
  - `resource` (`ResourceSummary`), `provider` (`PersonSummary`)
  - `available` (boolean, лише в `GET /slots/{slot_id}`) — чи можна забронювати зараз
- **Зв'язки:** належить ресурсу; має не більше одного активного бронювання (INV-01).
  Хто забронював слот, API не розкриває (SEC-004).
- **Вимоги:** FR-010, FR-011, FR-020…FR-023.

### Ресурс `bookings`

- **Кінцеві точки:** `POST /bookings`, `GET /bookings/{booking_id}`,
  `POST /bookings/{booking_id}/cancel`, `POST /bookings/{booking_id}/reschedule`,
  `GET /me/bookings`
- **Опис:** запис студента на слот; бачить і змінює його лише власник.
- **Атрибути:**
  - `id` (uuid)
  - `state` (enum `active` | `in_progress` | `completed` | `cancelled`) — похідний стан
    з `data-model.md` §7; `in_progress` закриває AQ-05
  - `slot` (`id`, `starts_at`, `ends_at`), `resource`, `provider`
  - `cancel_deadline_at` (date-time) — фіксується під час бронювання (FR-041, FR-065)
  - `can_cancel` (boolean) — чи можна зараз скасувати або перенести (US-014)
  - `created_at`, `cancelled_at`, `cancellation_kind` (`student` | `provider_block` |
    `rescheduled`), `cancellation_reason`, `rescheduled_to_id`
- **Зв'язки:** належить студенту й слоту; перенесене бронювання посилається на нове
  (`rescheduled_to_id`, INV-14).
- **Вимоги:** FR-030…FR-036, FR-040…FR-045.

### Поточний користувач

- **Кінцева точка:** `GET /auth/me` → `id`, `full_name`, `email`, `roles[]` (FR-007).
  `roles` — список: модель даних допускає кілька ролей (AQ-01).

**Чого API не віддає.** Хеші паролів, токени, e-mail інших користувачів і те, хто
забронював слот. Відповіді містять лише ім'я провайдера (`PersonSummary`) — мінімум
персональних даних (SEC-004, `data-model.md` §6).

## 4. Проєктні рішення

### 4.1. Чому Code-First

Ми обрали підхід Code-First, тому що:

- **одне джерело правди.** Схема Pydantic одночасно валідує запит і описує його в
  специфікації: обмеження `ge`, `le`, `multiple_of`, `pattern` потрапляють в OpenAPI як
  `minimum`, `maximum`, `multipleOf`, `pattern`. Документація не може розійтися з
  перевіркою, бо це той самий рядок коду;
- **розходження ловитиме CI після PR-8.** `python scripts/export_openapi.py --check`
  порівнює закомічений `openapi-generated.yaml` зі згенерованим; після додавання цього
  кроку в `build` ручна правка YAML або забута перегенерація ламатиме збірку;
- **повноту анотацій перевіряють тести.** `tests/api/test_contract.py` проходить по всій
  специфікації: опис кожної операції, опис кожного параметра й поля, приклад кожної
  помилки, `401` для кожної захищеної операції. Нова кінцева точка без анотацій не
  пройде CI;
- **ітерації швидші.** Зміна коду → перезапуск `uvicorn --reload` → оновлений YAML і
  Swagger UI за кілька секунд.

**Відхилена альтернатива — Design-First** (YAML вручну, далі код). Вона потрібна, коли
контракт узгоджують кілька команд до написання коду (Лекція 4, §2). У нас споживач API —
власний Web UI, тож контракт узгоджуємо в рецензії PR; ручний YAML лише додав би друге
джерело правди, яке розходиться з кодом.

**Як це працює:** код у `src/api/` → `app.openapi()` (FastAPI) → `openapi_export.py`
записує YAML і каталог помилок `errors.html` → під час старту сервера, скриптом або в
конвеєрі `api-docs.yml` на кожен push у `main` → GitHub Pages.

### 4.2. Дії над бронюванням: `POST .../cancel` замість `DELETE`

Скасування — не видалення: скасоване бронювання лишається в історії студента
(`GET /me/bookings`, FR-036) і в даних про те, хто й коли скасував (THR-08). Тому:

- `POST /bookings/{booking_id}/cancel` — дія, яка застосовує правила вікна скасування
  (FR-040, FR-041) і повертає оновлене бронювання (`state: cancelled`);
- `POST /bookings/{booking_id}/reschedule` — атомарна заміна, що створює нове
  бронювання (тому `201` і `Location` нового).

**Відхилені альтернативи:** `DELETE /bookings/{booking_id}` — семантика «ресурсу більше
немає» не відповідає збереженій історії, а повторне скасування має пояснити стан (409), а не
повернути «успіх» ідемпотентного `DELETE`; `PATCH {"state": "cancelled"}` — клієнт міг би
спробувати виставити будь-який стан, а правила переходів розмазалися б між валідацією
полів і бізнес-логікою.

### 4.3. Коди стану

| Код | Коли | Приклад |
|---|---|---|
| `200` | успішне читання або дія без створення ресурсу | `GET /slots`, `POST .../cancel` |
| `201` + `Location` | створено ресурс; `Location` — його адреса | `POST /bookings`, `POST .../reschedule` |
| `401` + `WWW-Authenticate` | немає або невідомий токен | `AUTH_REQUIRED` |
| `403` | роль не дозволяє операцію або об'єкт чужий | `FORBIDDEN_ROLE`, `NOT_OWNER` |
| `404` | об'єкта з таким ідентифікатором немає | `BOOKING_NOT_FOUND` |
| `409` | запит коректний, але конфліктує з поточним станом або часом | `SLOT_ALREADY_BOOKED`, `CANCELLATION_DEADLINE_PASSED` |
| `422` | запит некоректний незалежно від стану системи | `VALIDATION_FAILED`, `SLOT_IN_PAST` |
| `503` + `Retry-After` | тимчасовий конфлікт транзакцій після повтору (ADR-002, п. 6) | `TRANSIENT_CONFLICT` |
| `500` | непередбачена помилка; без подробиць | `INTERNAL_ERROR` |

**Правило 409 чи 422.** Якщо той самий запит міг би пройти за іншого стану системи —
`409` (слот звільниться, граничний час ще не настав для іншого бронювання). Якщо запит
неправильний за будь-якого стану — `422` (тривалість 17 хв, час без поясу, дата поза
горизонтом пошуку). Звідси `SLOT_IN_PAST` — `422`, а `SLOT_STARTED` у бронюванні — `409`:
слот існує й був придатний, але час минув.

**Чому 403, а не 404, для чужого бронювання.** Так визначає HLD §5.1 і THR-03: студент
дізнається, що це питання доступу, а не помилка в посиланні. Перебір ідентифікаторів
непрактичний — це UUIDv4 (DD-13), а тіло відповіді не містить жодних даних об'єкта.
Альтернативу «404 для чужого» розглянули: вона ховає факт існування, але ускладнює
діагностику, а з UUID виграш мінімальний.

**Чому дія повертає `200` з тілом, а не `204`.** Клієнт одразу отримує новий стан
(`state`, `can_cancel`) без другого запиту.

### 4.4. Обробка помилок

Єдина структура для всіх відмов (DD-07) — RFC 9457 `application/problem+json`. Вона
містить усі складники структури помилки з Лекції 4 (§3.5), але в стандартних полях:

| Лекція 4 | UniSlot | Навіщо |
|---|---|---|
| `error.code` | `code` | стабільний машинний код (`SLOT_ALREADY_BOOKED`), за ним розгалужується клієнт |
| `error.message` | `title` + `detail` | `title` однаковий для типу проблеми, `detail` пояснює цей випадок |
| `error.details[]` | `errors[]`: `field`, `message`, `type` | помилки окремих полів, лише для `VALIDATION_FAILED` |
| `error.request_id` | `request_id` | той самий, що в заголовку `X-Request-ID` і в журналі сервера |
| `error.documentation` | `type` | URI рядка в каталозі `errors.html` на GitHub Pages |
| — | `action` | що користувач може зробити далі (USAB-001) |
| — | `status`, `instance` | статус дублює HTTP-код, `instance` — шлях запиту |

Окремі типи проблем мають розширення: `BOOKING_LIMIT_REACHED` — `limit` і
`active_bookings` (US-001: «називає поточний ліміт і кількість»),
`CANCELLATION_DEADLINE_PASSED` — `cancel_deadline_at` (US-002).

**Чого немає в тілі помилки — свідомо.** Значення, яке надіслав клієнт (`provided_value` з
прикладу Лекції 4). Під час огляду чужого коду (`docs/code-quality/review-report.md`) ми
знайшли саме цю вразливість, CWE-209: коли бракує обов'язкового поля, Pydantic кладе у
`input` усе тіло запиту, і воно поверталося клієнтові разом із можливим паролем. У нас
обробник бере з помилки валідації лише `loc`, `msg` і `type` (`errors.py`, `_field_errors`),
а тест `test_validation_error_does_not_echo_input` це перевіряє. Немає також трасування
стека й назв внутрішніх класів: `500` має загальне повідомлення, подробиці — у журналі з тим
самим `request_id`.

**Повний каталог** — 25 типів проблем у `CATALOG` (`src/api/errors.py`), опублікований як
`errors.html`. Кожна операція перелічує в специфікації свої можливі причини для кожного коду
й має приклад тіла на кожну причину.

**Приклади в анотаціях.** Тіла запитів мають іменовані приклади, серед них і навмисно
некоректні («Помилка: тривалість 17 хв (422)»), а параметри шляху — приклади ідентифікаторів
демо-даних («Власне активне бронювання», «Бронювання іншого студента»). Swagger UI показує їх
списком і підставляє значення, тож кожну відповідь, зокрема `403` і `409`, видно без
копіювання UUID. MCP-сервер, згенерований з API (бонус), бере описи інструментів із тих
самих анотацій.

### 4.5. Стратегія пагінації

Дві стратегії за типом списку (Лекція 4, §3.3):

| Список | Стратегія | Чому |
|---|---|---|
| `GET /resources`, `GET /me/bookings` | зсув: `limit`, `offset`; у відповіді `total`, `has_more` | списки малі (десятки записів), інтерфейсу потрібна загальна кількість і перехід на сторінку |
| `GET /slots` | курсор: `limit`, `cursor`; у відповіді `next_cursor`, `has_more` | найбільший і найчастіший запит (PERF-001: 5 000 слотів); набір вільних слотів змінюється під час гортання — зсув пропускав би або дублював слоти; курсор за `(starts_at, id)` стабільний |

- Ліміт за замовчуванням — 20, максимум — 100 (більше → `422`); `offset` — до 10 000.
- Курсор непрозорий (base64url позиції останнього елемента); зіпсований курсор — `422` з
  полем `query.cursor`.
- Наявність наступної сторінки визначає прийом «limit + 1» — без окремого підрахунку.

**Відхилена альтернатива — одна стратегія для всіх списків.** Зсув у пошуку слотів
повертав би той самий слот на двох сторінках, якщо між запитами хтось забронював слот з
першої сторінки; курсор для каталогу з чотирьох ресурсів позбавив би адміністратора
загальної кількості без реальної вигоди. Ціна рішення — дві схеми метаданих
(`OffsetPagination`, `CursorPagination`), обидві в обгортці `{items, pagination}`.

### 4.6. Валідація вхідних даних

- **Схема — перша лінія.** Типи, межі й формати — в Pydantic (`extra="forbid"`: невідоме
  поле дає `422`, а не ігнорується — захист від mass assignment, THR-04). Обмеження A-005
  (`duration_minutes`: `ge=15`, `le=120`, `multiple_of=5`) видно прямо в специфікації.
- **Час — лише з поясом.** `starts_at` має тип `AwareDatetime`: «10:00» без поясу
  неоднозначний між зимовим і літнім часом (A-007).
- **Правила, що залежать від стану, — у сервісах:** `SLOT_IN_PAST`, `DATE_OUT_OF_HORIZON`,
  `PROVIDER_NOT_ELIGIBLE` (INV-15), `SLOT_OVERLAP` (FR-011).
- **PATCH розрізняє «не передали» і «передали null».** Відсутнє поле не змінюється;
  `null` для обов'язкового поля — `422`, а не «тихе» ігнорування; порожній PATCH — `422`. Це
  урок із нашого огляду чужого коду, де явний `null` губився (`review-report.md`, п. 1).
- **Помилка вказує поле:** `errors[].field` — `body.capacity`, `query.limit`,
  `path.booking_id`.

### 4.7. Ідемпотентність бронювання

`POST /bookings` приймає необов'язковий заголовок `Idempotency-Key` (8–64 символи). Якщо
зв'язок обірвався після створення бронювання, клієнт повторює запит із тим самим ключем і
отримує **те саме** бронювання (`201`, заголовок `Idempotent-Replayed: true`), а не нове.
Той самий ключ з іншим тілом — `422 IDEMPOTENCY_KEY_REUSED`.

- Ключ діє в межах користувача. У заглушці записи живуть до перезапуску; у справжній
  реалізації — 24 год у PostgreSQL.
- `POST .../cancel` ключа не потребує: повтор після успіху повертає
  `409 BOOKING_ALREADY_CANCELLED`, і клієнт бачить, що мета досягнута.
- Ідемпотентність доповнює REL-001, а не замінює: від двох **різних** студентів захищає
  інваріант бази даних (ADR-002), від повтору **того самого** запиту — ключ.

| Перевірка власника в сервісі; `403` без даних об'єкта | `booking_service.get_owned`, `slot_service.create_slot` | SEC-004, THR-03 |

### 4.9. Версіонування

- **MAJOR — у шляху:** `/api/v1`. Шлях змінюється лише з несумісною зміною стабільного
  контракту.
- **Повна версія — семантична:** `info.version` = `1.0.0-alpha.1` у специфікації й
  заголовок `API-Version` у кожній відповіді. Значення задане в одному місці коду
  (`config.API_VERSION`), звідти його беруть і специфікація, і middleware.
- **Чому `alpha`.** Поки відповідають заглушки, а автентифікація тимчасова (§5), контракт
  ще може змінитися несумісно — суфікс попереджає про це за правилами semver. Стабільний
  `1.0.0` — коли модулі замінять заглушки (орієнтовно Лаб 8, разом із журналом змін).
- **Несумісні зміни** (після `1.0.0` — лише в `/api/v2`): вилучення чи перейменування
  поля відповіді; нове обов'язкове поле запиту; зміна змісту коду помилки чи статусу; зміна
  схеми автентифікації. **Сумісні:** нове необов'язкове поле, нова кінцева точка, новий код
  помилки для нового сценарію.
- **Виведення з ужитку:** заголовки `Deprecation`, `Sunset` і `Link` з
  `rel="successor-version"`, обидві версії паралельно до дати `Sunset`, інструкція міграції.

### 4.10. Час і часові пояси

Усі моменти часу у відповідях — RFC 3339 в UTC (`2026-10-20T07:30:00Z`), як і в БД (A-007).
Показ за Києвом — завдання інтерфейсу. Виняток — фільтр `date` у пошуку: «20 жовтня» для
студента означає київську дату, тому фільтр порівнює саме її. Вхідний `starts_at` приймає
будь-який пояс (`+02:00`, `Z`) і зберігається в UTC.

## 6. Обмеження заглушок

- Дані в пам'яті: перезапуск сервера повертає демо-дані до початкового стану, створене не
  зберігається.
- Час демо-слотів відраховується від моменту запуску (завтра о 10:00 за Києвом тощо);
  після кількох днів роботи без перезапуску демо-сценарії зсуваються в минуле.
- Сервіси-заглушки працюють зі схемами API напряму; у Лаб 5 між ними з'явиться доменний шар
  (HLD §6).
- Журнал аудиту адміністративних дій ведеться в пам'яті й не має кінцевої точки перегляду.
- Сповіщення (FR-050…FR-054) не надсилаються: outbox і worker — окремі компоненти (ADR-003).

## 7. Як змінювати API

1. Змінити код у `src/api/` (роутер, схему чи заглушку) з анотаціями: `summary`, докстрінг,
   `response_description`, `problem_responses(...)` для кожного коду помилки, описи полів.
2. Сервер із `--reload` перезапуститься й перезапише `docs/api/openapi-generated.yaml`;
   перевірити зміну в Swagger UI (`/api-docs`).
3. `python -m pytest` — контракт-тести скажуть, чого бракує в анотаціях.
4. Закомітити код **разом** із перегенерованими `openapi-generated.yaml` і `errors.html`.
5. CI (`build`) перевіряє тести; після PR-8 він також перевірятиме розходження
   специфікації. Після злиття `api-docs.yml`
   публікує нову документацію на GitHub Pages.
