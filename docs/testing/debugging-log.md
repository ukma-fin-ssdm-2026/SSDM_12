## 0. Як проводити челендж

Одна людина вносить помилку й не каже іншим, яку саме. Решта налагоджує. Документатор
веде журнал.

```shell
cd <корінь репозиторію>
git apply docs/testing/debug-challenge/bug-01-pagination.patch
```

Правила, без яких вправа втрачає сенс:

- Той, хто налагоджує, **не запускає** `git diff` чи `git status`, щоб знайти зміну. Це
  дає відповідь, нічого не навчивши. У реальному інциденті diff подивитися нема де.
- Не читати розділ 7, доки помилку не знайдено.
- Виправляти причину, а не симптом. «Додати 1 до `totalPages`» — не виправлення.
- Сесія завершена тоді, коли є тест, що падає до виправлення й проходить після.

Повернення у вихідний стан:

```shell
git apply --reverse docs/testing/debug-challenge/bug-01-pagination.patch
```

## 1. Симптом

Те, що сказав репортер, дослівно — більше в того, хто налагоджує, нічого немає:

> Список готелів показує лише одну сторінку. У dev-середовищі 15 готелів, а пагінатор
> застряг — «Далі» неактивна. Перші десять показуються нормально. Минулого тижня

Запит для відтворення:

```
GET /v1/api/hotels?limit=10
```

Метадані отриманої відповіді:

| Поле           | Значення |
|----------------|----------|
| `totalItems`   | 15 |
| `items.length` | 10 |
| `totalPages`   | **1** |
| `currentPage`  | 0 |
| `limit`        | 10 |

Очікуване `totalPages`: 2.

## 2. Метод

Цикл, застосований протягом усієї сесії, по одному кроку за раз, із записом результату
кожного **до** того, як щось буде змінено в коді:

1. **Відтворити** на вимогу. Немає відтворення — немає налагодження.
2. **Сформулювати очікуване й фактичне** як два конкретні значення, а не як відчуття.
3. **Ділити навпіл конвеєр, а не вихідний код.** На кожному кроці — спостереження, що
   вдвічі звужує зону підозри.
4. **Інструментувати заради фактів.** Не змінювати поведінку, доки триває діагностика.
5. **Висунути одну спростовну гіпотезу** й придумати найдешевше спостереження, яке її
   вбило б.
6. **Виправити першопричину**, потім довести це тестом, що без виправлення падає.
7. **Розбір польотів**: чому наявний набір тестів цього не впіймав.

## 3. Журнал сесії

### Крок 1 — відтворити детерміновано

`HotelRepositoryStub` тримає дані в пам'яті, тож dev-дані — це те, що встигли надіслати
через POST. Засіяти відомі 15 готелів, тоді запитати. Сенс у фікстурі, яка падає
**щоразу**; переривчасте відтворення з'їдає решту сесії.

**Результат:** відтворено. `totalPages = 1` при `totalItems = 15`, кожен прогін.

### Крок 2 — відокремити «хибні дані» від «хибних метаданих»

Два зовсім різні дефекти виглядають з інтерфейсу однаково: або пошук повертає замало
готелів, або лічильник правильний і хибна лише арифметика сторінок.

Відповідь уже їх розрізняє. `totalItems` — **15**, правильно. `items` містить
**10** — правильно для `limit=10`. Хибне лише `totalPages`.

**Висновок:** репозиторій, фільтри й сервіс поводяться коректно. Усе, що нижче шару API,
відсіяно одним спостереженням, без читання жодного рядка. Це найцінніший крок сесії.

### Крок 3 — знайти єдиного власника хибного поля

```shell
grep -rn "totalPages" spectrum-app/src/main/java
```

Одне присвоєння, у конструкторі `PageResponse`. Більше ніхто в це поле не пише, а
`HotelPageResponse` лише успадковує `PageResponse`, нічого не перевизначаючи.

**Висновок:** дефект усередині `PageResponse`, в одному виразі.

### Крок 4 — відтворити без HTTP-стека

`PageResponse` — звичайний клас. Створити його напряму, замість піднімати Quarkus і
слати запит: секунди на ітерацію замість хвилини, і з переліку підозрюваних зникають
серіалізація, маршрутизація та зв'язування `@BeanParam`:

```java
new PageResponse<>(List.of(), 15, new PaginationParams(0, 10)).getTotalPages();
```

**Результат:** повертає `1`. Відтворено ізольовано. HTTP-шар невинний.

### Крок 5 — прочитати вираз і подивитися його історію

```shell
git log -p -1 -- spectrum-app/src/main/java/.../page/PageResponse.java
```

Гіпотеза, сформульована так, щоб її можна було вбити: *`totalItems / params.limit()` —
це цілочисельне ділення, тож залишок, тобто неповна остання сторінка, відкидається ще
до того, як `Math.max` його побачить.*

Спростовний тест: якщо гіпотеза правильна, помилка має **зникати** щоразу, коли
`totalItems` кратне `limit`. Якщо пагінатор працює на 20 готелях і ламається на 21 —
гіпотеза витримала. Якщо ламається й на 20 — гіпотеза хибна.

### Крок 6 — підтвердити таблицею входів

Обидві формули поруч, на випадках, що мають значення:

```

         0      10        1        1 same
         1      10        1        1 same
         9      10        1        1 same
        10      10        1        1 same
        11      10        2        1 DIFFERENT -> 1 item(s) unreachable
        15      10        2        1 DIFFERENT -> 5 item(s) unreachable
        20      10        2        2 same
        21      10        3        2 DIFFERENT -> 1 item(s) unreachable
```

Гіпотеза підтверджена, і та сама таблиця пояснює репортерове «минулого тижня
працювало»: формули збігаються на 0, 1, 9, 10 і 20 елементах. Будь-який набір даних,
менший за сторінку або кратний її розміру, ховає помилку повністю. Минулого тижня в
dev-середовищі було 10 готелів.

## 4. Першопричина

```java
// до — правильно
this.totalPages = (int) Math.max(1, Math.ceil((double) totalItems / params.limit()));

// після — внесений дефект
this.totalPages = (int) Math.max(1, totalItems / params.limit());
```

Прибране зведення `(double)` перетворює ділення з рухомою крапкою на цілочисельне.
`Math.ceil` після цього нема чого округлювати вгору, тож його прибрали як «зайвий».
Неповна остання сторінка відкидається й стає недосяжною: клієнтові повідомляють, що її
не існує.

Важко помітити це саме через `Math.max(1, …)`. Він там для того, щоб порожній результат
усе одно звітував про одну сторінку, — і водночас мовчки лагодить випадок
`totalItems < limit`, тобто рівно той, на якому перевіряють руками.

Класифікація: **дефект із втратою даних**, не косметичний. Кожен елемент за останньою
повною сторінкою недосяжний через API.

## 5. Виправлення й регресійний тест

Виправлення — повернути зведення типу. Більше нічого не потрібно: `Math.max(1, …)`
далі робить свою справжню роботу, обробляючи порожню сторінку.

Регресійні тести — у `PageResponseTest`:

- `roundsUpToCoverThePartialLastPage` — одинадцять випадків, зокрема 11/10, 15/10,
  21/10 і 100/7. Кожен падає за наявності дефекту.
- `totalPagesTimesLimitCoversEveryItem` — перебір 0–60 елементів проти лімітів 1–12 із
  твердженням інваріанта `totalPages * limit >= totalItems`. Це саме та властивість,
  яку порушує помилка, записана як властивість, а не як набір прикладів, — тож вона
  ловить і варіації, яких ніхто не додумався перелічити.

Падає також `HotelControllerTest.getHotelsRespondsWithAPage`: він стверджує 3 сторінки
для 25 елементів при ліміті 10.

Перевіряти виправлення слід у правильному порядку — тест спершу має впасти:

```shell
cd spectrum-app
./mvnw test -Dtest=PageResponseTest          # очікуємо падіння, дефект ще застосовано
cd .. && git apply --reverse docs/testing/debug-challenge/bug-01-pagination.patch
cd spectrum-app
./mvnw test -Dtest=PageResponseTest          # очікуємо зелене
```

Тест, якого ніколи не бачили червоним, нічого не доводить про помилку, яку він нібито
покриває.

## 6. Розбір польотів

**Чому набір тестів цього не впіймав.** У `PageResponse` не було тестового класу взагалі.
Дефект сидить у найчастіше використовуваному арифметичному виразі шару API, і жоден тест
його не виконував. Це рівно та прогалина, яку мав знайти Test-a-Thon; вона записана
першим рядком аналізу прогалин у [`coverage-report.md`](coverage-report.md).

**Чому його не впіймали б інші гейти.** Spotless лише форматує. У SpotBugs немає
детектора на «це цілочисельне ділення мало бути з рухомою крапкою» — обидві форми
легальні й ідіоматичні. А `.github/workflows/github-actions-test.yml` виконує
`echo "Hello, World!"`, тож жодне завдання CI не запустило б тести, навіть якби вони
існували (знахідка **F-4**).

**Що пришвидшило пошук.** Крок 2. Прочитати `totalItems = 15` поруч із `totalPages = 1`
означало відсіяти репозиторій, фільтри, сервіс і мапери одним спостереженням — усю
нижню половину стека — ще до того, як хтось відкрив файл. Якби сесія почалася з читання
`HotelRepositoryStub.search`, найскладнішого коду у функціональності й природного
першого підозрюваного, дорога до того самого місця коштувала б значно більше.

**Що пришвидшило б ще більше.** Якби твердження-інваріант
`totalPages * limit >= totalItems` існувало заздалегідь. Тести на прикладах ловлять
лише ті приклади, які хтось придумав; цей інваріант ловить увесь клас помилок
округлення.

**Виконані дії**

| № | Дія | Стан |

| 1 | Регресійні тести округлення `PageResponse`, включно з перебором інваріанта | Готово — `PageResponseTest` |
| 2 | JaCoCo у збірці з порогом на рівні класу, щоб клас із нульовим покриттям валив гейт | Готово — `coverage-report.md`, розділ 1 |
| 3 | Змусити CI справді виконувати `./mvnw clean verify` | Відкрито — знахідка **F-4** |

## 8. Нотатки про прийоми

Варте збереження для наступного інциденту, незалежно від цієї конкретної помилки.

| Прийом | Коли окупається | Як |
|--------|-----------------|-----|
| Звузити до відтворення на звичайних об'єктах | Майже завжди | Вийти з HTTP-стека, щойно шар визначено. Час ітерації падає з хвилини до секунди. |
| Запускати один тест, а не весь набір | Щільний цикл на відомому падінні | `./mvnw test -Dtest=PageResponseTest#roundsUpToCoverThePartialLastPage` |
| `git bisect` | «Минулого тижня працювало», а діапазон більший за кілька комітів | `git bisect start; git bisect bad; git bisect good <tag>`, а `git bisect run ./mvnw -q test -Dtest=PageResponseTest` автоматизує перебір |
| `git blame` на звуженому рядку | Щойно вираз знайдено | `git blame -L 12,18 -- <файл>` дає коміт, автора, у якого можна спитати, і намір із повідомлення |
| Умовна точка зупину | Цикл, що падає лише на деяких ітераціях | Зупинятися на `totalItems % limit != 0`, а не крокувати через кожен виклик |
| Твердження-інваріант замість прикладів | Арифметика, округлення, межі | Стверджувати властивість (`totalPages * limit >= totalItems`), а не перелік випадків |
| Таблиця входів навколо межі | Підтвердження гіпотези про off-by-one чи округлення | Вивести правильне й підозріле поруч, як у кроці 6; те, де вони збігаються, зазвичай і пояснює, чому помилку не помічали |
