# Стратегія тестування UniSlot — Лаб6

Основна частина, близько однієї сторінки. Актуально на 27.10.2026, main `6a627b7`.
Власник — Никита; огляд — Денис.

**Стан.** 236 тестів: 162 unit-випадки у 12 файлах, API-контракти та property-тести.
Unit перевіряють домен Booking і сервіси без HTTP: часові межі, пагінацію, атомарність
перенесення, валідацію ресурсів. Fixture скидає in-memory store і фіксує годинник;
Mock ізолює залежність, tmp_path — файловий експорт. API-рівень перевіряє статус,
авторизацію, RFC 9457 та OpenAPI. Це ще не тести реальної PostgreSQL чи UI.

**Покриття.** Рядки 98.08%, гілки 93.88%, разом
97.51% по всьому `api`+`unislot`, gate 90%.
MCP transport не запускався (0% `mcp_server.py`), startup/CLI й деякі аварійні гілки
покриті частково. Прогалини явні в [HTML](lab06/htmlcov/index.html),
не вилучені з метрики. Coverage показує виконання, а не доводить правильність.

**Наступні рівні.** Після PostgreSQL-адаптера — інтеграційні тести міграцій,
FK/UNIQUE/EXCLUDE, rollback перенесення й конкурентного бронювання одним слотом із двох
з'єднань; детерміновані fixtures та окрема тестова БД. Після з'єднання UI/API —
системні тести пошук→бронювання→перенесення→скасування. Приймальні сценарії за US/RTM:
студент змінює лише своє, провайдер створює лише свої слоти, адміністратор керує ресурсами;
очікування на межах дедлайну й київського дня узгоджуємо перед реалізацією.

**Спеціальні перевірки.** PERF-001 виміряти на 5000 слотів за узгодженим p95,
числом паралельних клієнтів і сталим стендом; теперішній TestClient не є навантажувальним
доказом. Для безпеки — матриця ролей/власності, вимкнена demo auth за замовчуванням,
неправильні курсори, витоки даних, залежності й секрети. Property testing уже перевіряє
round-trip курсора та 100 неправильних JSON id; далі — часові інваріанти й перетини.

**CI та підтримка.** На кожному PR — чинні Ruff/format, Bandit, detect-secrets,
pip-audit, import contracts, requirements/архітектура, OpenAPI; далі весь pytest із branch
coverage, gate 90%, HTML/JSON/JUnit як artifacts. Gate не знижуємо для проходження:
регресія означає дописати тести або узгодити зміну. Власник зміненого модуля оновлює тести;
Аксенія публікує свіжі звіти, Павло перевіряє workflow, Денис веде debugging-log.
Перед здачею потрібні власні TDD-коміти, огляд і два Loom від кожного.

## Бонуси — додаток поза основною сторінкою

1. **Mutation:** [звіт](lab06/mutation-report.md), 38 мутантів, 89.47%→100.00%;
   описано вцілілий `is`→`==` і новий тест. Пояснює Павло у своєму відео.
2. **Property:** `tests/property/test_cursor_shapes.py`, Hypothesis генерує 100
   неправильних значень `i`: None, числа, списки. Інваріант — 422 VALIDATION_FAILED,
   поле `query.cursor`, без серверного винятку. Пояснює Денис або Павло.
3. **CI gate:** `.github/workflows/ci.yml` на реальному Windows runner застосовує сукупний
   поріг **90%** для `api`+`unislot` через `scripts/run_lab06.py` — та сама команда локально
   і в CI, тож розбіжність між ними неможлива. Запроваджено в PR-08 (#207).
   **Чому 90%, а не виміряні 97.51%.** Поріг має ловити регресію, а не падати від кожної
   нової гілки коду: впритул до фактичного рівня він зробив би червоним будь-який наступний
   PR, і команда почала б його знижувати — саме цього ворота й мають не допускати. 90%
   лишає запас на ріст коду й зупиняє збірку при втраті значної частини покриття.
   **Доказ, що ворота працюють, а не завжди зелені:** при `--cov-fail-under=90` прогін
   проходить ([gate-positive.txt](lab06/evidence/gate-positive.txt)), при
   `--cov-fail-under=100` зупиняє збірку з кодом 1
   ([gate-negative.txt](lab06/evidence/gate-negative.txt)); набір тестів в обох випадках
   однаковий — 236 passed, падають саме ворота.
   URL зеленого Actions run додає Павло — він же пояснює бонус у своєму відео.
