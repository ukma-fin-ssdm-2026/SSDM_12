### 1.2. Сильні сторони (3)

1. **Таблиця «НЕ тестуємо» з причиною й лабораторною для кожного пункту.** Плани зазвичай фіксують лише те, що входить в обсяг. Тут видно, що саме виведено за межі, чому (немає PostgreSQL, немає адаптера сповіщень, OQ-001 не закрито) і коли повернеться. Рецензент не мусить вгадувати, пропуск це чи рішення.
2. **Колонка «Стан» разом із §5.** Розрізнення `є` / `частково` / `новий` дає побачити реальний стан автоматизації, а фактичні числа прогону (96 passed, 94% branch) супроводжені застереженням, що прогін був на Linux / Python 3.13, а CI — Windows / Python 3.12. План не видає локальний прогін за доказ CI — і це саме те, що розрізняє звіт від обіцянки.
3. **Ризик R1 названий там, де тест зелений.** Зафіксовано, що `test_concurrent_requests_give_one_201` не доводить REL-001, бо працює проти in-memory сховища під GIL, а не проти СУБД із транзакціями. Команди зазвичай зараховують зелений тест як доказ; тут зелений тест свідомо залишено зі статусом «частково», а повний доказ винесено окремим рядком 11.

### 1.3. Зони для покращення (2)

1. **Внутрішня суперечність обсягу й критеріїв виходу** — мітка: **Blocking**. Критерій 4 вимагає повного покриття тест-кейсів обсягу, критерій 1 — зеленого CI для всіх рядків, а в таблиці 11 рядків, один із яких у CI не запускається. За цими критеріями план не може бути завершений ніколи. *Пропозиція:* визнати план ризик-орієнтованою вибіркою, перелічити відкладені тест-кейси окремим розділом, уточнити критерії 1, 2 і 4.
2. **Модулі без жодної згадки** — мітка: **Blocking**. Notifications, Auth і аудит адміністративних дій не з'являються ні в таблиці, ні у виключеннях. *Пропозиція:* додати їх до таблиці «НЕ тестуємо» з причиною «модуля немає в `src/api/`» і цільовою лабораторною.

### 3.1. Чим перевірено, а не «на око»

Пункти 1 і 4 не оцінюються читанням — під них є інструменти. Прогін на клоні `cb95d33`, 2026-10-19:

```
ruff check --select F src tests scripts     → All checks passed
  (F401 невикористані імпорти, F821 невизначені імена, F841 мертві змінні — 0)

vulture src tests --min-confidence 80       → 2 знахідки
  src/api/schemas/resources.py:87  unused variable 'cls'
  src/api/schemas/resources.py:117 unused variable 'cls'

перебір членів ErrorCode по src/                → 25 з 25 підіймаються
перебір членів ErrorCode по tests/              → 4 не згадані за іменем
пошук "except:" / "except Exception" по src/    → 0 збігів
```

Обидві знахідки `vulture` — **хибні спрацювання**: `cls` — перший параметр валідатора Pydantic, позначеного `@classmethod`; інструмент не бачить виклику, бо валідатор викликає фреймворк. Перевірено читанням `src/api/schemas/resources.py`.

Реальність пакетів із `requirements.txt` підтверджується непрямо: крок CI `Install API dependencies` встановлює їх із закріпленими версіями й падає, якщо пакета чи версії не існує. Прямого перевіряння по PyPI в межах цієї активності не робили.

### 3.2. Висновок

Код проходить огляд за всіма чотирма інструментально перевіреними пунктами. Єдина знайдена прогалина не в коді, а в тестах: чотири шляхи помилок не закріплені жодним твердженням, тож перейменування коду в `ErrorCode` зламає контракт мовчки. Заведено як окреме завдання, не як блокер цього PR. Пункт 5 заповнює рецензент після обговорення.

## 4. Рефлексія

**Які аспекти тест-планів найчастіше ігноруються** (наші спостереження на цій активності):

- **Межі обсягу.** Те, що свідомо не тестується, не записують узагалі — і потім неможливо відрізнити рішення від пропуску. У нашому першому варіанті так випали цілі модулі (Notifications, Auth, аудит).
- **Критерії виходу пишуть як гасла, а не як перевірки.** «Покриття достатнє», «немає критичних дефектів» без числа й без джерела числа. Наш критерій 2 був таким самим, поки огляд не змусив підставити 85.
- **Критерії виходу не звіряють із власною таблицею.** Два з п'яти наших критеріїв суперечили змісту плану — це видно за хвилину, але лише якщо читати їх разом, а не поспіль.
- **Зелений тест автоматично зараховують як доказ вимоги.** Найдорожча зі звичок: `test_concurrent_requests_give_one_201` зелений і стосується REL-001, але нічого про REL-001 не доводить.

**Що було неочікувано корисним у внутрішньому огляді:**

- Найцінніші зауваження стосувалися не таблиці тест-кейсів, на яку пішла більшість часу, а трьох рядків над нею. Таблицю рецензент читає й погоджується; суперечності живуть у критеріях виходу.
- Корисним виявився сам примус пройтися чек-лістом по порядку. Пункт 5 («виконуваний у CI») поставив питання, якого ніхто не ставив під час написання: а чи запуститься рядок 11 у наявному конвеєрі. Відповідь — ні.
- Правило «кожне "Ні" — із міткою й пропозицією» не дало огляду перетворитися на перелік претензій: чотири Blocking-зауваження перетворилися на чотири конкретні правки за один прохід.
