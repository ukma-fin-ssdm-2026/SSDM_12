## Як зібрано дані (відтворюється)

```bash
# 1. перелік запусків на main (пагінація, бо за 3 тижні їх >100)
for p in 1 2 3; do
  gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/actions/runs?branch=main&per_page=100&page=$p" \
    --jq '.workflow_runs[] | {id,name,head_sha,conclusion,created_at,run_started_at,updated_at,event}'
done

# 2. таймінги завдань кожного запуску (startedAt / completedAt)
gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/actions/runs/<id>/jobs?per_page=100"

# 3. PR, з якого злито коміт, і перший коміт цього PR

gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/pulls/<n>/commits?per_page=100"   # [0].commit.author.date

# 4. причина червоного запуску
gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/check-runs/<job_id>/annotations"
gh run view <id> --log-failed

# 5. спроби запуску, що мав повтор (run_attempt > 1): висновок і jobs кожної спроби
gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/actions/runs/<id>/attempts/<n>"
gh api "/repos/ukma-fin-ssdm-2026/SSDM_12/actions/runs/<id>/attempts/<n>/jobs"

# 6. увесь Етап 1 одним запуском — скрипт бонусу 1 (ті самі запити, той самий результат)
python scripts/dora_metrics.py --since 2026-10-19 --until 2026-11-09 --out docs/ci-cd/dora-auto.md
```

## Визначення стовпців

| Стовпець | Визначення |
|---|---|
| **Коміт** | `head_sha` запуску — коміт злиття PR у `main` |
| **PR** | PR, з якого походить коміт (`/commits/<sha>/pulls`); **усі 104 коміти мають рівно один змерджений PR** — прямих пушів у `main` у вікні немає |
| **Перший коміт PR** | `authoredDate` першого запису в `/pulls/<n>/commits` — початок відліку часу виконання змін |
| **Запуск завершено** | `completedAt` останнього завдання запуску |
| **Черга, хв** | старт **останньої спроби** (`run_started_at`; для першої спроби = `createdAt`) → `startedAt` її першого завдання |
| **Виконання, хв** | `startedAt` першого завдання → `completedAt` останнього (тієї самої спроби) |
| **Статус** | ✅ success · ❌ failure · ⏹️ cancelled |

> **Важливо для тлумачення «Виконання»:** у `ci.yml` два завдання (`build`, `reliability`), але раннер
> **один** (`SSDM12-Windows`, `runs-on: [self-hosted, Windows, X64]`), тому вони **не виконуються
> паралельно** — друге чекає, поки звільниться машина. Тож «виконання» для таких запусків — це сума
> двох завдань плюс внутрішнє очікування, а не час найдовшого завдання.

### Навантаження на раннер (поза `main`)

Той самий єдиний раннер обслуговує і перевірки PR (`on: pull_request`). За те саме вікно:

| Подія | Запусків `CI` | ✅ | ❌ |
|---|--:|--:|--:|
| `pull_request` (гілки) | 213 | 182 | 31 |
| `push` (`main`) | 104 | 96 | 6 (+2 ⏹️) |
| **Разом** | **317** | **278** | **37** |

> 317 запусків за 21 день на одній машині ≈ 15 запусків/день ≈ **88 хв зайнятості раннера на добу**
> (за середнім виконанням 5,8 хв). Середнє навантаження невелике — проблема у **пачках**:
> медіана черги 0,05 хв, але p90 = 8,7 хв і max = 368,8 хв (запуск №20, 24.10 вночі).

### 31 червоний запуск на гілках PR проти 6 на `main`

Це не недогляд, а свідчення, що **шлюз на PR працює**: той самий `build` є обов'язковою
перевіркою PR, тому дефекти зупиняються до злиття. Усі 6 червоних на `main` (і обидві приховані червоні
спроби №40 і №56) — **інфраструктурні** (див. §3 `dora-summary.md`), жоден не є дефектом коду,
