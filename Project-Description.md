**Команда:** SSDM_12 · **Репозиторій:** `ukma-fin-ssdm-2026/SSDM_12`

## 1. Опис ідеї

Запис студентів на консультації до викладачів і бронювання навчальних аудиторій на
факультеті сьогодні відбувається через розрізнені канали: чати, електронну пошту та усні
домовленості. Наслідки передбачувані — слоти губляться, двоє студентів приходять на той
самий час, скасування не доходить до другої сторони, а викладач не бачить власного
завантаження на тиждень наперед. Немає ані єдиного джерела правди про зайнятість ресурсу,
ані історії, до якої можна апелювати.

UniSlot — вебсистема, у якій провайдер ресурсу (викладач або відповідальний за аудиторію)
публікує доступний час, студент знаходить і бронює вільний слот, а адміністратор керує
ресурсами, ролями та політиками бронювання. Система гарантує відсутність накладок навіть за
одночасних спроб, надсилає нагадування та веде журнал аудиту адміністративних дій.
Користувачі системи — та сама аудиторія, що її розробляє, тому вимоги збираються з реальних
респондентів, а не з вигаданих персон.

## 2. Міні-ТЗ

### 2.1. Призначення системи

UniSlot розв'язує проблему неузгодженого бронювання обмежених у часі ресурсів факультету
(консультацій викладачів і навчальних аудиторій) для трьох груп користувачів: студентів,
яким потрібен передбачуваний запис і нагадування; провайдерів, яким потрібен контроль над
власним часом і видимість завантаження; адміністрації, якій потрібні єдиний реєстр ресурсів,
керовані політики та простежуваність дій.

### 2.2. Межі системи

**У обсязі цього семестру**

- Автентифікація та розмежування прав за трьома ролями.
- Публікація доступності: разові слоти та щотижневий повторюваний шаблон.
- Пошук вільних слотів із фільтрами; бронювання, скасування, перенесення.
- Політики бронювання: вікно скасування, ліміт активних бронювань на користувача.
- Сповіщення (підтвердження, нагадування, скасування) — через внутрішній адаптер із
  заглушкою замість реального провайдера доставки.
- Панель адміністратора: ресурси, користувачі, ролі, політики, журнал аудиту.
- REST API як єдина точка входу для всіх операцій.

**Свідомо поза обсягом**

- Платежі та будь-які фінансові операції.
- Нативні мобільні застосунки (вебінтерфейс адаптивний, цього достатньо).
- Інтеграція з реальними інформаційними системами НаУКМА (розклад, деканат, SSO).
- Двостороння синхронізація із зовнішніми календарями (Google Calendar, iCal).
- Чат чи обмін повідомленнями між учасниками.
- Правила повторення, складніші за щотижневі (місячні, за винятками, за календарем свят).
- Багатомовність інтерфейсу.
- Реальна доставка e-mail/SMS — адаптер сповіщень має заглушку, а не зовнішнього провайдера.

*Рішення, яке варто назвати явно:* сповіщення залишено в обсязі попри спокусу їх викинути.
Вони дають системі зовнішню залежність, відмову якої можна ін'єктувати та обробити (див.
NFR-5). Викинути їх означало б спростити реалізацію ціною втрати найважливішої властивості —
поведінки системи під час часткової відмови.

### 2.3. Ролі користувачів

| Роль | Що може робити |
|---|---|
| **Студент** | Переглядати каталог ресурсів і вільних слотів; бронювати слот; скасовувати та переносити власне бронювання в межах політики; бачити список своїх бронювань та отримувати нагадування |
| **Провайдер** (викладач / відповідальний за аудиторію) | Публікувати доступність разовими слотами та щотижневим шаблоном; блокувати час; підтверджувати або відхиляти заявки, якщо ресурс потребує підтвердження; бачити календар і завантаження власних ресурсів |
| **Адміністратор** | Створювати й редагувати ресурси; призначати провайдерів; керувати користувачами та ролями; задавати політики (вікно скасування, ліміти); читати журнал аудиту |

### 2.4. Ключові функції

1. **F1. Автентифікація та авторизація** — реєстрація, вхід, розмежування прав за трьома ролями.
2. **F2. Керування доступністю** — провайдер публікує разові слоти та щотижневий шаблон, блокує окремі проміжки.
3. **F3. Пошук вільних слотів** — фільтри за провайдером, типом ресурсу, датою, місткістю; горизонт до 14 днів.
4. **F4. Бронювання** — створення бронювання з перевіркою конфліктів, лімітів і політик; гарантія відсутності накладок.
5. **F5. Скасування та перенесення** — зміна або скасування бронювання відповідно до політики вікна.
6. **F6. Сповіщення** — підтвердження, нагадування та повідомлення про скасування через адаптер сповіщень.
7. **F7. Адміністрування та журнал аудиту** — керування ресурсами, ролями й політиками; незмінний запис адміністративних дій.

### 2.5. Нефункціональні вимоги

Кожна вимога сформульована так, щоб її можна було перевірити тестом або виміром.

| # | Атрибут якості | Вимога | Спосіб перевірки |
|---|---|---|---|
| **NFR-1** | Продуктивність | Пошук вільних слотів на горизонті 14 днів повертає відповідь за **≤400 мс (p95)** при 50 одночасних користувачах, 5 000 слотів і 200 користувачів у базі | Навантажувальний сценарій, звіт у `docs/testing/` |
| **NFR-2** | Надійність / конкурентність | При **100 одночасних** запитах на бронювання одного слота успішним завершується **рівно один** (`201`), решта отримує `409`; частка подвійних бронювань — **0** | Інтеграційний тест із паралельними запитами |
| **NFR-3** | Безпека | Паролі зберігаються лише як солоні повільні хеші (**Argon2id** або bcrypt з cost ≥ 12); **100%** негативних кейсів RBAC-матриці повертають `403`; жоден секрет не потрапляє в репозиторій | Тести RBAC-матриці; статичний аналіз безпеки в CI (Bandit + secret scanning) |
| **NFR-4** | Приватність | Студент не має доступу до персональних даних інших студентів через жоден ендпоінт; **100%** адміністративних дій над ресурсами й ролями потрапляють у журнал аудиту | Тести на доступ до чужих ресурсів; перевірка повноти журналу |
| **NFR-5** | Відмовостійкість | Недоступність адаптера сповіщень **не блокує** створення бронювання: операція завершується за **≤2 с**, сповіщення ставиться в чергу повторних спроб | Ін'єкція збою в адаптер сповіщень (Лаб 9) |
| **NFR-6** | Підтримуваність | Покриття доменного модуля бронювання тестами **≥70%**; SonarCloud Security Rating — **A** | Звіт покриття (Лаб 6), SonarCloud (Лаб 8) |

Мінімальна вимога курсу — три NFR, з яких щонайменше одна про безпеку чи приватність.
Тут їх шість, бо NFR-2, NFR-5 і NFR-6 наперед задають те, що команда доводитиме в
Лабораторних 6, 8 і 9; дешевше специфікувати це зараз, ніж дописувати заднім числом.

### 2.6. Припущення та обмеження

**Технологічний стек**

| Шар | Вибір |
|---|---|
| Мова та фреймворк | Python 3.12, FastAPI |
| Доступ до даних | SQLAlchemy 2.x, Alembic |
| База даних | PostgreSQL 16 |
| Тестування | pytest, pytest-cov |
| Якість коду | Ruff (лінтер + формат), **Bandit** (статичний аналіз безпеки), SonarCloud |
| CI/CD | GitHub Actions |
| Локальне середовище | Docker Compose |
| Клієнт | Мінімальний вебінтерфейс поверх того самого REST API |

*Обґрунтування вибору:* силабус називає Bandit і PyTest першими прикладами інструментів для
Лаб 5 і Лаб 6, тож стек дає нульове тертя з вимогами курсу. PostgreSQL обрано замість SQLite
свідомо: NFR-2 про конкурентність недоказова без справжніх транзакцій і рівнів ізоляції.

**Обмеження та припущення**

- Зовнішніх платних сервісів не використовуємо; доставка сповіщень — локальна заглушка.
- Дані в системі синтетичні; реальні персональні дані студентів і викладачів не зберігаються.
- Команда — 4 особи, орієнтовно 7 годин самостійної роботи на тиждень на людину протягом
  11 тижнів (силабус: 76 годин самостійної роботи).
- Розгортання демонструється локально через Docker Compose; публічний хостинг — необов'язкова
  ціль Лаб 10, не зобов'язання.
- Обсяг зафіксовано на дату документа. Розбіжності між міні-ТЗ і реалізацією фіксуються в
  `docs/requirements/` під час Лаб 2 і далі, а не приховуються.

## 3. Відкриті питання обсягу

Винесені в GitHub Issues з міткою `scope` та вирішуються на найближчій зустрічі команди.

1. Чи всі бронювання автоматично підтверджуються, чи певні типи ресурсів вимагають підтвердження провайдером? (Впливає на модель станів бронювання в Лаб 3.)
2. Яка політика вікна скасування — фіксована для всієї системи чи налаштовується адміністратором на рівні ресурсу?
3. Чи потрібен список очікування (waitlist) на зайнятий слот, чи це поза обсягом семестру?
4. Чи входить самореєстрація студентів, чи облікові записи створює адміністратор?
