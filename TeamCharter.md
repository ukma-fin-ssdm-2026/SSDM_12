## 4. Співпраця та робочий процес

- **Стратегія гілкування:** GitHub Flow. Гілка функції від `main`
  (`feature/<назва>`, `fix/<назва>`, `docs/<назва>`) → Pull Request → злиття.
  Прямий push у `main` заблоковано захистом гілки (ruleset `main-protection`).
  Довгоживучі гілки не створюються.
- **Практики комітів:** малі коміти, кожен із самодостатнім повідомленням про причину
  зміни. Формат — Conventional Commits: `feat:`, `fix:`, `docs:`, `ci:`, `test:`,
  `refactor:`, `chore:`. Кожен учасник комітить під власним акаунтом GitHub.
- **Огляди коду:** кожне злиття в `main` вимагає Pull Request і **щонайменше одного
  схвалення**. Автор не схвалює і не мерджить власний PR. Схвалення анулюються при
  надходженні нових комітів. Усі коментарі в огляді мають бути закриті до злиття.
- **Строк на огляд:** автор одразу після відкриття Pull Request призначає рецензента у
  полі Reviewers і повідомляє в основному каналі. Якщо рецензії немає протягом 24 годин,
  її зобов'язаний дати наступний учасник за черговістю зі списку в розділі 1. Pull Request
  не може стояти без рецензії довше 48 годин; після цього питання виноситься на зустріч
  команди. Автоматичне призначення рецензента за зонами відповідальності забезпечує
  [`.github/CODEOWNERS`](.github/CODEOWNERS).
- **Чужі гілки:** гілку з відкритим Pull Request перейменовує, змінює або видаляє лише
  її автор.
- **Робочий процес завдань:** створити issue → призначити виконавця й мітки → гілка →
  коміти → Pull Request із посиланням `Closes #N` → схвалення → злиття → issue
  закривається автоматично. Деталі — у [`CONTRIBUTING.md`](CONTRIBUTING.md).
- **Визначення готовності (Definition of Done):** зміна вважається готовою, коли вона
  пройшла PR, отримала схвалення, конвеєр CI зелений, а відповідний документ у `docs/`
  оновлено.

### 4.1. Огляд артефактів вимог

- **Користувацькі історії.** Рецензія дається окремим коментарем до кожної історії:
  чи зрозуміла роль і цінність, чи є негативний критерій, чи відповідає історія INVEST.
  Схвалення без коментаря по суті не зараховується як огляд.
- **Нефункціональні вимоги.** Кожна NFR проходить чек-лист вимірюваності: названо
  характеристику й підхарактеристику ISO/IEC 25010; є число з одиницею й порогом;
  названо умови вимірювання; зрозуміло, чим і коли вимірюємо та в якій лабораторній
  з'явиться доказ; результат вимірювання однозначно каже «виконано» або «не виконано»;
  є джерело й пріоритет. Чек-лист проходить спільна сесія огляду NFR, яку веде
  Керівник якості; висновки записуються в Pull Request.
- **Матриця простежуваності.** Оновлюється в тому самому Pull Request, що змінює
  історію або вимогу, а не наприкінці роботи. Якщо ідентифікатор у матриці не існує
  у вихідному файлі, Pull Request не зливається.
- **Числові значення.** Пороги й ліміти живуть лише в `requirements.md` §6 як A-###.
  Історії та вимоги посилаються на ідентифікатор, а не повторюють число — інакше
  зміна політики потребує правок у кількох місцях, і одне з них неодмінно забувають.

### 4.2. Управління артефактами вимог

- Усі документи вимог лежать у `docs/requirements/`: `requirements.md`,
  `user-stories.md`, `rtm.md`. Інших місць для них немає.
- Ідентифікатори наскрізні для всіх трьох файлів і не перевикористовуються: вилучена
  вимога закреслюється з посиланням на issue, а її номер не займає нова. Конвенції
  й діапазони — на початку `requirements.md`.
- README містить розділ «Артефакти вимог» з описом і посиланнями на всі три файли.
  Підтримувати його в актуальному стані — обов'язок Керівника документації; посилання
  перевіряються клацанням після кожного злиття, що додає або перейменовує документ.
- Автоматичне призначення рецензентів за зонами відповідальності задає
  [`.github/CODEOWNERS`](.github/CODEOWNERS). Кожен файл вимог має двох власників,
  щоб автор Pull Request не лишався без рецензента.

## 5. Вирішення конфліктів

1. **Обговорення по суті.** Розбіжність виноситься на зустріч або в коментарі до PR;
   аргументи формулюються навколо фактів і наслідків для проєкту, а не навколо осіб.
2. **Голосування більшістю.** Якщо консенсусу немає — просте голосування чотирьох.
3. **Розв'язання нічиєї.** У команді з чотирьох осіб можлива нічия 2:2. У такому разі
   вирішальний голос має власник ролі, у чиїй зоні відповідальності лежить питання
   (архітектурне — Repo Maintainer, обсяг — Project Brief Lead, конвеєр — CI Maintainer).
   Рішення та причину фіксуємо в issue.
4. **Ескалація.** Якщо питання не розв'язано протягом двох робочих днів або стосується
   участі й навантаження — звертаємося до викладача.

Технічні розбіжності, які переживуть тиждень, оформлюються як ADR у `docs/architecture/`
починаючи з Лабораторної 3.

## 8. Використання ШІ

Розділ узгоджено з [Політикою використання ШІ](https://ssdm-2026.cs-courses.org/ai-policy.html)
курсу: використання дозволене й очікуване, вирішує не факт використання, а спосіб верифікації.

### 8.1. Інструменти команди

- **Чат-асистенти:** Claude (Anthropic), ChatGPT (OpenAI) — специфікація завдань, чернетки
  документації, пояснення концепцій, огляд власного коду.
- **Кодові агенти та асистенти в IDE:** Claude Code, GitHub Copilot — генерація коду,
  тестів і конфігурацій у межах поставленої специфікації.
- Перелік поповнюється рішенням команди; поява нового інструмента фіксується комітом у
  цей розділ.

### 8.2. Правила розкриття

- Кожен суттєвий артефакт (документ у `docs/`, значна зміна коду, конфігурація) містить
  нотатку **«Використання ШІ»**: що згенеровано, яким інструментом, як перевірено, що
  зроблено вручну.
- В описі Pull Request автор зазначає, чи є в змінах згенерований код і як він верифікований.
- На пряме запитання викладача про використання ШІ відповідаємо точно.

### 8.3. Правило верифікації

- Згенерований код проходить ті самі механізми, що й написаний вручну: прочитання автором
  перед комітом, тести, статичний аналіз, взаємний огляд.
- **Неперевірений згенерований код не потрапляє в `main`.** Технічно це забезпечує захист
  гілки: злиття неможливе без PR, схвалення та зеленого CI.
- Кожен учасник відповідає за кожен рядок, який здає, незалежно від того, хто його написав.
  Нездатність пояснити власний внесок на захисті трактується як його відсутність.
- Не передаємо в зовнішні сервіси персональні дані одногрупників і закриті матеріали курсу.
- Не публікуємо як результат те, чого не перевіряли: вигадані метрики, результати тестів
  або джерела є порушенням доброчесності, а не помилкою.
